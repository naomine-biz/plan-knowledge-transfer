# 知識移転計画：エンジニアリーダーのためのMySQL最新アップデート

## 承認用の要約

- **目的**：最新の更新がアプリケーションとDBのどこを変え、利用・更新・検証にどんな条件があるかを、システム全体の関係から理解する。
- **想定読者**：MySQLを使うサービスのエンジニアリーダー。SQL、トランザクション、接続、レプリカの用途は知っている。サーバのスレッド管理、レプリケーションの適用方式、GTID、PQCは既知としない。
- **目標**：Lv5。クライアントの接続と要求、サーバでの処理、レプリカへの更新の適用、通信の成立、観測と回復を結び付け、更新が作用する場所と条件を捉える。
- **確認日と範囲**：2026-10-08。最新GAの26.7系列を中心とし、LTSの9.7系列との関係を整理する。26.7.1はDockerイメージだけのセキュリティ更新、26.10.0はEarly Accessとして区別する。
- **主要な更新**：Community EditionでのThread Poolの提供、Change Stream Applier、TLS 1.3のPQC対応。バージョン表記・配布物・互換性も、利用条件として扱う。
- **理解の順序**：リリースの範囲と既存の処理 → 更新が変える仕組み → 適用できない条件 → 自分の性能・互換性の見立ての点検 → 更新後のシステムの全体像。
- **状態**：v2、読者ペルソナの指摘を反映、再点検中、Humanの承認待ち。

## 目的・前提と到達目標

依頼で与えられた条件は、テーマが「MySQL最新アップデートの紹介」、読者がエンジニアリーダーであること。MySQL 8.4など既存のMySQLを使うアプリケーションを担当し、個別の新機能の内部モデルは未習得であるという条件は、サンプルのために置いた仮定である。

読者が最終的に獲得する理解は、次の三つとする。

- **G1**：確認日時点のGA・LTS・Early Access、機能が加わる更新と配布物に限定した修正を区別し、対象としている版と提供範囲を特定できる。
- **G2**：Thread Pool、Change Stream Applier、PQC対応が、それぞれ要求処理・更新の適用・通信の確立をどう変え、どんな設定・構成・相手側の条件を必要とするか理解できる。
- **G3**：G1・G2を、アプリケーションの応答、レプリカの新鮮さ、リソース、接続互換性、更新経路、観測と回復へ結び付け、更新後のシステムが成立する条件を捉えられる。

計画担当の全体像は、クライアントの要求が接続を通じてサーバへ届き、処理とコミットが行われ、更新がレプリカへ伝わる系である。最新の更新は、そのうち異なる箇所に作用する。新機能の利用条件と、既存の構成・アプリケーションの条件を対応させて初めて、更新の意味を判断できる。

## 理解の項目

以下の識別子は理解と依存関係を示す。本文の章・節・段落や、図表の配置を指定するものではない。

### A：対象と、変更前のシステムを特定する

- **A1**：LTSとInnovationでは、機能変更の頻度・サポート期間・更新経路が異なり、最新の機能と既存環境の更新先を区別する必要があることを理解する。
- **A2**：9.7が従来の連番表記の最後の系列であり、以降の版が年・月に基づく表記へ移るため、26.7の数字を従来のメジャーバージョンの差と同じ意味で読まないことを理解する。
- **A3**：26.7.0の機能更新、Dockerイメージだけを対象とする26.7.1のセキュリティ更新、26.10.0のEarly Accessは、利用できる機能と配布状態が異なることを理解する。
- **A4**：アプリケーションの接続、サーバでの要求処理、コミット、更新ログ、レプリカでの適用は異なる役割であり、応答時間とレプリカの新鮮さに関係することを理解する。

**前提と寄与**：A1〜A3は読者の既存版の利用経験とS1〜S4を使ってG1を満たす。A4は接続・トランザクション・レプリカについての既知の内容を具体化し、G2の出発点にする。

### B：接続と要求処理の関係を理解する

- **B1**：標準の接続ごとのスレッドと、多数の接続が同時に処理を要求する状況を結び付け、実行するスレッド数による切り替えや資源競合の負担を理解する。
- **B2**：サーバのThread Poolが、接続と実行するスレッドの対応・並行度を管理する仕組みであり、アプリケーション側で接続を再利用するConnection Poolとは役割が異なることを理解する。
- **B3**：26.7.0でCommunity EditionでもThread Poolが提供され、プラグインを読み込んで利用するため、アップデートしたこととその仕組みが動作していることを区別できることを理解する。

**前提と寄与**：B1はA4、B2はB1、B3はB2とS5を使い、G2の要求処理とG3のリソースの関係を支える。

### C：更新の伝播と適用の関係を理解する

- **C1**：レプリケーションが、更新の受信・ログへの保存・トランザクションの適用・コミットからなり、適用側の待ち時間もレプリカの遅延に関係することを理解する。
- **C1.1**：チャネルが、ある送信元からの受信・適用・進捗を管理する単位であり、CSAの選択と資源の設定がこの単位に対応することを理解する。
- **C2**：GTIDがトランザクションを識別し、適用済みの更新を区別するために使われることと、行ベースのログが更新された行の情報を伝えることを理解する。
- **C2.1**：GTIDで適用済みのトランザクションを把握すると、未適用の更新を送信元へ要求して再開する自動位置決定につながることを理解する。
- **C3**：Change Stream Applier（CSA）が、依存関係を満たすトランザクションの適用を並行化し、コミット順序を保つ設定が有効な場合には適用とコミット順序の待機を分けることを理解する。
  - **C3.1**：先行する更新に依存するトランザクションと、並行に適用できるトランザクションを区別し、適用を終えたこととコミットの順番が来たことの違いを理解する。
  - **C3.2**：従来方式ではコミットの順番を待つワーカーがその間使えなくなる一方、CSAではその待機を切り離してワーカーが別の実行可能なトランザクションを適用できる関係を理解する。
- **C4**：CSAの選択とワーカー・イベントメモリの設定がチャネルごとに行われるため、各チャネルの処理と資源を対応させられることを理解する。
- **C5**：CSAは明示的に選ぶ方式で、新規チャネルの既定は従来のMulti-Threaded Applierであることを理解する。CSAには行ベースのログ、GTIDの構成、チャネルの自動位置決定などの前提があり、設定変更では適用を停止する必要があることを理解する。

**前提と寄与**：C1・C1.1はA4、C2・C2.1はC1・C1.1、C3はC1・C2、C4はC1.1・C3、C5はC2〜C4とS6を使い、G2の適用方式とG3のレプリカの成立条件を支える。

### D：PQC対応が変える通信の関係を理解する

- **D1**：TLSで通信を始めるときに、接続する双方が使用する鍵交換などの方式を合意することを理解する。
- **D2**：26.7のPQC対応は、OpenSSL 3.5.0以降を用いるTLS 1.3接続で、従来方式とPQCを組み合わせた方式などを利用するための対応であることを理解する。
  - **D2.1**：PQC（Post-Quantum Cryptography、耐量子計算機暗号）が、将来の量子計算機による一部の従来の公開鍵暗号への攻撃を想定した方式であり、TLSの鍵交換や認証の保護に関係することを理解する。
  - **D2.2**：OpenSSLがTLSなどを実装する暗号ライブラリであり、使える方式はその実装・版と、接続する双方の対応に依存することを理解する。
- **D3**：PQCの利用を要求する設定、相手側の対応、実際に合意した方式が、接続の成立と保護の条件になることを理解する。通信で使う方式と、保存されたデータの暗号化を区別する。
  - **D3.1**：通常のクライアント接続と非同期レプリケーションの接続は、要求するPQCの設定と通信経路を別々に対応させる必要があることを理解する。前者の`force_pqc`と後者の`replication_force_pqc`を区別し、実際に合意した方式で接続の成立を確かめる。

**前提と寄与**：D1は接続についての既知の内容を使う。D2はD1とS2・S9、D3はD1・D2とS2を使い、G2の通信の確立とG3の接続互換性を支える。

### E：適用条件を変えて、新機能の意味を検討する

- **E1**：接続数、同時実行、処理時間、資源の競合が変わればThread Poolの影響も変わるため、機能の提供から、自分の処理の高速化までを無条件につなげられないことを理解する。
- **E2**：CSAが並行化できる範囲はトランザクションの依存関係や資源に左右され、ワーカーを増やすことと遅延を減らすことの成立条件を区別する。
- **E3**：行ベース・GTIDの条件を満たさないチャネルや遅延レプリケーションでは、CSAを同じ条件で利用できないことを理解する。
- **E4**：PQCを要求する設定とクライアントの対応が合わない場合、通信の保護を強める変更が接続の成立に影響することを理解する。
- **E5**：新機能の利用とは別に、プラットフォームや設定・振る舞いの変更が既存環境に作用することを理解する。26.7のEnterprise Linux 7対応終了と、AUTO_INCREMENTの予約を有効にした場合の異常終了後の欠番を、その具体的な条件として捉える。

**前提と寄与**：E1はB、E2・E3はC、E4はD、E5はA1〜A3とS2を使い、G2・G3の成立範囲を定める。

### F：自分の期待と比較条件を根拠に照らして点検する

- **F1**：「新機能が使える」「設定で有効にした」「自分の負荷で改善した」という異なる確認を区別し、自分の推論がどこまで原典と測定に支えられているか点検できることを理解する。
- **F2**：性能比較に使った接続数・同時実行・処理・レプリケーションの依存関係が、自分のアプリケーションを代表する条件か点検できることを理解する。
- **F3**：版の数字や記事の見出しから置いた「全配布物に適用される」「全機能が既定で有効」「版を戻せば復旧できる」という前提を、S1〜S8の提供範囲・設定・更新条件に照合して点検できることを理解する。

**前提と寄与**：F1はB3・C5・D3・E、F2はB1・C3・E1・E2、F3はA・S7・S8を使い、G3で利用する根拠の範囲をそろえる。

### H：更新後のシステム全体を結び付ける

- **H1**：クライアント、接続の合意、サーバの実行資源、トランザクション、レプリケーションのチャネル、レプリカの読み取りを対応させ、各更新が作用する場所を捉えられることを理解する。
  - **H1.1**：書き込みの処理量が増える負荷では、送信元から出る更新も増え、受信・適用の能力との差がレプリカの遅延と読み取りの新鮮さへ伝わることを理解する。
  - **H1.2**：読み取り要求とレプリケーションの適用が同じサーバのCPUやI/Oを使う場合、各処理の並行度と資源競合が、応答と適用の進捗の両方に影響することを理解する。
- **H2**：構成と設定に対応する接続の成否、要求の待ち時間、資源の使用、レプリカの適用状況・エラーを観測し、実際の改善と機能の成立を区別できることを理解する。
  - **H2.1**：PQCは対象経路の接続と合意方式、Thread Poolは有効化・実行待ち・資源と応答、CSAは選択した方式・ワーカーの動作・受信と適用の進捗・エラーへ、観測を対応させることを理解する。
- **H3**：現行版、配布物、OS・ライブラリ、クライアント、プラグイン、レプリカを、対応する更新経路と利用条件へ照合する必要があることを理解する。
  - **H3.1**：既存のデータファイルを新しいサーバで使う更新と、別のサーバへデータを移して切り替える更新では、使う方法と互換性の条件が異なることを理解する。現行系列・対象系列・方法の組み合わせから、対応する遷移と必要な中間系列が決まる関係を理解する。
  - **H3.2**：更新中に送信元・レプリカ・クライアントが異なる版になる場合、更新ログを受信・適用できる組み合わせと接続できる条件を保つように、更新の順序と読み書き先を対応させることを理解する。
- **H4**：更新前のバックアップと復旧の条件、更新後の書き込みの扱いが、障害時に戻せるデータとサービスの条件を決めることを理解する。
  - **H4.1**：バックアップが表す時点と、それ以降に確定した更新を区別し、回復方法がその更新をどこまで扱えるかによって、復元後のデータの状態が決まることを理解する。
  - **H4.2**：回復先の版がデータ・使用した機能を扱えることと、アプリケーションの接続・読み書きが成立することを対応させ、データを戻す条件とサービスを再開する条件を捉えることを理解する。

**前提と寄与**：H1はA4・B・C・D、H2はH1・F1・F2、H3はG1・C5・D3・E5・S7、H4はH3・F3・S8を使い、G3を満たす。

自社の現行版、負荷、クライアント、配置、復旧目標は未提示である。このサンプルは更新の仕組みと適用条件の理解を目的とし、個別環境の更新可否や実行手順を確定しない。
