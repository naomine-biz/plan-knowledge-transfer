# MySQL 26.7の主要な更新は、システムのどこに作用するのか

**エンジニアリーダー向けに、Thread Pool・Change Stream Applier・PQC対応の仕組みと利用条件を整理する**

確認日：2026-10-08

MySQLの最新GAである26.7系列では、次の三つの更新が加わりました。

- Community EditionでのThread Poolの提供
- レプリカでの新しい適用方式であるChange Stream Applier（CSA）
- TLS 1.3での耐量子計算機暗号（PQC）への対応

どれも「速くなる」「安全になる」と短く紹介されがちですが、作用する場所はそれぞれ異なります。Thread Poolはサーバでの要求の処理を変えます。CSAはレプリカでの更新の適用を変え、PQC対応は接続の確立を変えます。また、どの更新も、版を上げただけでは働きません。それぞれに、設定、構成、接続相手についての条件があります。

この記事は、MySQL 8.4などを使うサービスを担当するエンジニアリーダーに向けて、次の順に進みます。

1. 対象の版と提供範囲を特定する
2. 変更前のシステムで、要求がレプリカへ届くまでの経路を確認する
3. 三つの更新が、その経路のどこをどう変えるかを見る
4. 機能の利用と効果が成立しない条件を確かめる
5. 自分の期待と、比較に使う条件を点検する
6. 観測・更新経路・回復を含めて、更新後のシステム全体を捉える

版・機能・利用条件は、公式のリリースノートとマニュアルで確認しました（末尾の「根拠」を参照）。一方、紹介する機能について、実サーバでの負荷試験や移行試験は行っていません。アプリケーションの要求と各機能の関係は、確認した仕様をもとにした整理と推論です。自社での改善幅や更新の可否は、この記事からは決まりません。

## 1. どの版の話かを特定する

### LTSとInnovationでは更新の性格が違う

MySQLのリリースは、LTS（Long-Term Support）とInnovationの二つの系列に分かれます。LTSは長期間サポートされます。系列内の更新は修正が中心で、振る舞いを変える機能の追加は原則として入りません。Innovationは、新機能や振る舞いの変更を短い間隔で取り込みます。次の版が出ると、サポートの対象もそちらへ移ります。

そのため、「最新の機能を知る」ことと「既存環境をどこへ更新するか決める」ことは、別の判断になります。新機能がInnovationで提供されても、運用中のLTS系列の更新に同じ機能が入るとは限りません。

### 26.7は「9から17上がった版」ではない

9.7は、従来の連番表記による最後の系列です。それ以降の版は、年・月に基づく表記に移りました。26.7は、2026年の7月にあたる系列を表します。

したがって、9.7から26.7への数字の差は、従来のメジャーバージョンの差と同じ意味を持ちません。数字の大きさから互換性の変化を推し量らないでください。変更の内容と対応する遷移は、リリースノートと更新経路の表で確かめます。

### 同じ系列でも、版ごとに中身と状態が違う

| 版 | 日付 | 状態 | 内容 |
|---|---|---|---|
| 26.7.0 | 2026-07-28 | GA（Innovation） | Thread PoolのCommunity Editionでの提供、CSA、PQC対応、対応OSや振る舞いの変更を含む機能更新 |
| 26.7.1 | 2026-08-18 | GA（Innovation） | MySQL ServerのDockerイメージだけを対象とするセキュリティ更新 |
| 26.10.0 | 2026-09-18 | Early Access | 次の系列の先行提供。本番の更新先にはしない |
| 9.7.1 | 2026-06-16 | GA（LTS） | 9.7系列で記載されている最新の更新。9.7.2は未リリース |

この表から読み取るべき点は二つあります。

第一に、26.7.1はDockerイメージに限った更新です。パッケージやバイナリで導入しているサーバは対象になりません。Dockerイメージを使う環境でも、26.7.1はサーバの機能を加える更新ではありません。イメージのセキュリティ修正として扱います。

第二に、26.10.0はEarly Accessです。そこに含まれる変更は、確認日の時点ではGAの機能として扱えません。

## 2. 変更前のシステム：要求はどこを通ってレプリカへ届くか

```
アプリケーション（Connection Pool）
   │ ① 接続の確立：TLSのバージョンと方式を合意する
   ▼
送信元サーバ
   │ ② 要求の処理：スレッドが文を実行する
   │ ③ コミット：確定した更新をバイナリログへ書く
   ▼
レプリカ
   │ ④ 受信：送信元へ接続し、更新を受け取ってリレーログへ保存する
   │ ⑤ 適用：トランザクションを適用し、コミットする
   ▼
レプリカからの読み取り
```

アプリケーションから見た応答時間は、主に①〜③で決まります。

一方、レプリカから読む内容がどれだけ新しいか（レプリカの新鮮さ）は別の区間で決まります。③で確定した更新が、④と⑤を経てレプリカでコミットされるまでの時間です。

三つの更新は、この経路の次の場所に作用します。

- **PQC対応**：①と、④でレプリカが送信元へ接続する経路
- **Thread Pool**：②
- **CSA**：⑤

以下では、まずそれぞれの場所で現在何が起きているかを確認します。そのうえで、更新がそれをどう変えるかを見ます。

## 3. Thread Pool：接続と、実行するスレッドの対応を変える

### 接続ごとのスレッドで起きること

標準のMySQLは、接続ごとに一つのスレッドを割り当て、その接続の文をそのスレッドが実行します。同時に処理を要求する接続が少なければ、この方式は単純で効率的です。

問題になるのは、多数の接続が同時に処理を要求する場合です。実行中のスレッドの数が、CPUのコア数を大きく超えます。OSはスレッドを切り替えながら実行し、スレッド同士はロック、サーバ内部の共有資源、CPUキャッシュを取り合います。

この切り替えと競合の負担が増えると、処理量が伸びないまま応答時間だけが延びます。負荷のピーク時に、性能が急に落ちることもあります。

### Thread PoolとConnection Poolは役割が違う

名前は似ていますが、二つは別の場所で、別の問題を扱います。

| | Connection Pool | Thread Pool |
|---|---|---|
| 場所 | アプリケーション側（ドライバ・フレームワーク） | サーバ側 |
| 管理するもの | 接続の確立と再利用、インスタンスごとの接続数 | 接続と実行するスレッドの対応、同時に実行する数 |
| 解決する問題 | 接続確立の費用、接続数の上限 | 多数の接続が同時に実行するときの切り替えと競合 |

アプリケーションのインスタンスが増えると、各インスタンスのConnection Poolの合計が、サーバの接続数になります。個々のConnection Poolは、自分の接続数を抑えられます。しかし、サーバ全体で同時にいくつの文が実行されるかは制御できません。

Thread Poolは、この全体の並行度をサーバ側で管理します。接続とそれを実行するスレッドを一対一に固定せず、同時に実行する数を抑えます。それを超えた要求は、実行を待たせます。

つまり、二つは置き換えの関係にはありません。組み合わせて使うものです。

### 26.7.0で変わったこと

Thread Poolは、これまでEnterprise Editionの機能でした。26.7.0からは、Community Editionでも提供されます。

ただし、Thread Poolはプラグインとして読み込んで使う仕組みです。サーバを26.7.0へ更新しただけでは、従来どおり接続ごとのスレッドで動きます。「26.7.0に更新した」ことと「Thread Poolが動作している」ことは、別の事実として確認してください。

```sql
-- 読み込みの指定とプラグイン名は「Thread Pool Installation」の記載に合わせる
SELECT PLUGIN_NAME, PLUGIN_STATUS
FROM INFORMATION_SCHEMA.PLUGINS
WHERE PLUGIN_NAME LIKE 'thread_pool%';
```

## 4. Change Stream Applier：レプリカでの適用を変える

CSAを理解するには、先に次の四つを押さえる必要があります。レプリケーションの段階、チャネル、GTID、行ベースのログです。

### レプリケーションの段階と遅延

レプリケーションは、次の四つの段階からなります。

1. **受信**：レプリカが送信元に接続し、バイナリログの更新を受け取る
2. **保存**：受け取った更新を、レプリカのリレーログへ書く
3. **適用**：リレーログのトランザクションを、レプリカのデータへ適用する
4. **コミット**：適用したトランザクションを確定する

レプリカの遅延とは、送信元でコミットされてから、レプリカでコミットされるまでの時間です。ネットワークや受信が十分に速くても、適用の段階でトランザクションが待たされれば、遅延は増えます。CSAが変えるのは、この適用側の待ちです。

### チャネル

チャネルは、ある送信元からの受信・適用・進捗をまとめて管理する単位です。

送信元が一つのレプリカにも、既定のチャネルが一つあります。複数の送信元から受け取るレプリカ（マルチソース）は、送信元ごとにチャネルを持ちます。後で述べるとおり、CSAを使うかどうかと資源の設定は、このチャネルの単位で行います。

### GTIDと行ベースのログ

GTID（Global Transaction Identifier）は、トランザクションごとに一意に付く識別子です。送信元のサーバを表す識別子と連番の組からなります。

レプリカは、適用済みのGTIDの集合を記録しています。そのため、あるトランザクションが適用済みかどうかを区別でき、同じ更新を二重に適用することを防げます。

この集合は、受信の再開にも使われます。レプリカは再接続のとき、「ここまで適用した」というGTIDの集合を送信元へ伝えます。送信元は、未適用のトランザクションだけを送ります。これが自動位置決定（`SOURCE_AUTO_POSITION=1`）です。ログのファイル名と位置を人が指定しなくても、受信を再開できます。

行ベースのログは、実行したSQL文ではなく、更新された行の内容をバイナリログに記録する形式です。レプリカは、文を再実行するのではなく、行の変更を適用します。

### 従来方式では、適用を終えたワーカーがコミットの順番を待つ

MySQL 8.4のレプリカは、既定で複数のワーカーを使うMulti-Threaded Applier（MTA）で動きます。また、コミット順序を保つ設定（`replica_preserve_commit_order`）も、既定で有効です。

このとき、適用の段階には性質の違う二つの待ちがあります。

- **依存による待ち**：先行するトランザクションと同じ行を更新するトランザクションは、先行するものの適用が終わるまで、適用を始められません。結果を正しく保つために必要な待ちです。
- **コミット順序による待ち**：依存のないトランザクションは並行に適用できます。ただし、送信元と同じ順序でコミットする設定では、適用を終えても、先行するトランザクションのコミットが済むまで、自分のコミットの順番が来ません。

ここで重要なのは、「適用を終えた」状態と「コミットの順番が来た」状態が別だという点です。

従来方式では、適用を終えたワーカーは、コミットの順番を待つあいだ次のトランザクションを扱えません。そのため、先頭に大きなトランザクションが一つあると、後続を適用し終えたワーカーが次々に待ちに入ります。並行に適用できるトランザクションが残っていても、使えるワーカーがなくなります。

### CSAは、適用とコミット順序の待ちを切り離す

CSAは、依存関係を満たしたトランザクションの適用を並行化する方式です。コミット順序を保つ設定が有効な場合、CSAは「適用」と「コミットの順番の待ち」を分けて扱います。

そのため、適用を終えたワーカーは、コミットの順番を待たずに、別の実行可能なトランザクションの適用へ移れます。コミット自体は、順序を保ったまま行われます。

```
従来方式（コミット順序を保つ）
ワーカー1 : [T1の適用 ..........................] → コミット
ワーカー2 : [T2の適用][T1のコミット待ち ......] → コミット
ワーカー3 : [T3の適用][T2のコミット待ち ......] → コミット
            T4〜T6は、空くワーカーがないため待つ

CSA
ワーカー1 : [T1の適用 ..........................]
ワーカー2 : [T2の適用][T4の適用][T5の適用]
ワーカー3 : [T3の適用][T6の適用]
コミット  : T1 → T2 → T3 → T4 → … の順序を保つ
```

この図は関係を示す模式図で、内部の実装を表すものではありません。図では、T4〜T6がT1〜T3と依存しないものとしています。

依存による待ちは、CSAでもなくなりません。たとえばT4がT1と同じ行を更新するなら、T4はT1の適用を待ちます。

### 設定はチャネルごとに行う

次の三つは、チャネルごとに設定します。

- CSAを使うかどうか
- ワーカーの数
- イベントを扱うメモリの量

これにより、チャネルの処理量に合わせて資源を割り当てられます。たとえば、負荷の大きい送信元のチャネルには、ワーカーとメモリを多く割り当てます。負荷の小さいチャネルには、少なく割り当てます。

### 既定と前提

CSAは、明示的に選ぶ方式です。新しく作るチャネルの既定は、従来のMTAです。26.7.0へ更新しただけでは、適用方式は変わりません。

CSAを選ぶには、チャネルが次の前提をすべて満たす必要があります。

| 前提 | 意味 |
|---|---|
| 行ベースのログ | 送信元が、更新を行の内容として記録する |
| `GTID_MODE=ON` | トランザクションをGTIDで識別する |
| `SOURCE_AUTO_POSITION=1` | チャネルが自動位置決定で受信する |
| `GTID_ONLY=1` | チャネルの進捗を、ログのファイル名と位置ではなくGTIDで扱う |
| `REQUIRE_ROW_FORMAT=1` | チャネルが、行ベース以外の形式の更新を受け付けない |
| `SOURCE_DELAY=0` | 適用を意図的に遅らせる遅延レプリケーションを使わない |

また、適用方式やその設定を変えるときは、チャネルの適用を停止する必要があります。停止中も送信元の更新は進むため、その間の更新は遅延として積み上がります。切り替えは、遅延を許容できる時間帯の作業として計画してください。

## 5. TLS 1.3のPQC対応：接続の成立を変える

### TLSでは、双方が方式を合意してから通信を始める

TLSで接続を始めるとき、クライアントとサーバは、使う方式を合意します。合意するのは、TLSのバージョン、暗号スイート、鍵交換の方式などです。あわせて、サーバの証明書などで相手を確かめます。

合意できるのは、双方が対応し、かつ設定で許している方式だけです。一方が新しい方式に対応していても、もう一方が対応していなければ、その方式は使われません。

### PQCとは

PQC（Post-Quantum Cryptography、耐量子計算機暗号）は、将来の大規模な量子計算機による攻撃を想定した暗号方式です。

現在のTLSの鍵交換や認証には、RSAや楕円曲線暗号などの公開鍵暗号が広く使われています。その一部は、そうした量子計算機によって破られる可能性があるとされています。NISTは2024年8月に、PQCの最初の三つの標準を確定しました。

TLSでは、鍵交換で共有した値をもとに、通信を暗号化する鍵を作ります。ここで、「通信を記録しておき、将来鍵交換が破られた時点で解読する」という攻撃を想定します。すると、鍵交換の保護は、量子計算機が実現する前から意味を持ちます。PQCが関係するのは、この鍵交換と認証の保護です。

なお、この記事は、量子計算機の実現時期や、自社の現在の暗号の耐性については何も主張しません。

### 26.7のPQC対応は、OpenSSLとTLS 1.3に結び付いている

OpenSSLは、TLSなどを実装する暗号ライブラリです。MySQLはTLSの処理にOpenSSLを使います。そのため、どの方式を使えるかは、MySQLが使うOpenSSLの実装と版に依存します。

26.7のPQC対応は、OpenSSL 3.5.0以降を用いるTLS 1.3の接続で、新しい方式を利用するための対応です。新しい方式には、従来の方式とPQCを組み合わせたものが含まれます。たとえば、楕円曲線のX25519とML-KEMを組み合わせた鍵交換です。

したがって、PQCを使った接続になるのは、次の条件がそろったときだけです。

- 接続がTLS 1.3である
- サーバ側がOpenSSL 3.5.0以降を用いている
- 接続相手も、PQCを含む方式に対応している

接続相手が対応しているかどうかは、クライアントが使うTLSの実装で決まります。OpenSSLを使うクライアントであれば、そのOpenSSLの版が条件になります。言語のランタイムが持つTLS実装を使うドライバであれば、そのランタイムの対応が条件になります。

PQCの利用を要求していなければ、サーバだけを更新しても、相手が対応していない接続は従来の方式で合意します。

### 要求する設定と、実際に合意した方式

PQCの利用を要求する設定を有効にすると、PQCを含む方式で合意できない接続は成立しなくなります。この設定は、経路ごとに分かれています。

| 経路 | 要求する設定 | 接続する側 |
|---|---|---|
| クライアント → サーバ | `force_pqc` | アプリケーションのドライバ、管理ツール、監視エージェントなど |
| レプリカ → 送信元（非同期レプリケーション） | `replication_force_pqc` | レプリカの受信 |

二つの設定は独立しています。クライアント接続でPQCを要求しても、レプリケーションの接続がPQCで保護されるわけではありません。逆も同じです。

どちらの経路でも、設定値を見るだけでは不十分です。実際に合意したTLSのバージョンと方式を確かめ、接続が成立していることを確認してください。

もう一点、区別すべきことがあります。PQC対応が変えるのは、通信路で使う方式です。テーブルスペース、バイナリログ、バックアップなど、保存されたデータの暗号化は別の仕組みであり、この対応では変わりません。

## 6. 利用と効果が成立しない条件

### Thread Pool：効果は負荷の形によって変わる

Thread Poolが効くのは、多数の接続が同時に実行を要求し、スレッドの切り替えや資源の競合が性能を下げている場合です。次のような場合、影響は小さいか、別の形で現れます。

- **同時に実行を要求する接続が少ない**：抑えるべき並行度が、もともと低い
- **実行時間の長い文やロック待ちが多い**：同時に実行する数を抑えることが、後続の要求の待ち方を変える。どう現れるかは、設定と負荷で確かめる必要がある
- **ボトルネックがI/Oや特定の行のロックにある**：同時に実行する数を抑えても、そのボトルネックは残る

接続数、同時実行、処理時間、資源の競合のどれかが変われば、Thread Poolの影響も変わります。「Community Editionで使えるようになった」から「自分のサービスが速くなる」へは、条件を確かめずにはつながりません。

### CSA：並行化できる範囲は、依存関係と資源で決まる

CSAが減らすのは、コミット順序の待ちによってワーカーが使えなくなっていた時間です。そのため、次の場合には効果が限られます。

- **同じ行を次々に更新するトランザクションが多い**：依存による待ちが支配的になり、並行化の余地が小さい
- **CPUやI/Oがすでに飽和している**：ワーカーを増やしても、適用は速くならない
- **遅延の原因が適用以外にある**：受信、ネットワーク、非常に大きな単一のトランザクションが原因なら、適用の並行化では解消しない
- **コミット順序を保つ設定を使っていない**：適用とコミット順序の待ちの分離は、この設定が有効な場合の話である

「ワーカーを増やした」ことと「遅延が減った」ことには、それぞれ別の成立条件があります。

### CSA：前提を満たさないチャネルでは使えない

次のチャネルでは、CSAを同じ条件で使えません。

- 文ベースや混合形式のログを使う送信元のチャネル
- GTIDを使っていないチャネル
- `SOURCE_DELAY`で適用を遅らせている遅延レプリカのチャネル

たとえば、操作ミスへの備えとして遅延レプリカを置いている構成では、そのチャネルは従来方式のまま残ります。

### PQC：保護を強める設定が、接続を止めうる

`force_pqc`を有効にすると、PQCを含む方式で合意できないクライアントは接続できなくなります。TLS 1.3で接続できないクライアントも同様です。対象には、古いドライバを使うバッチ、管理ツール、監視エージェントなど、普段は意識しないクライアントも含まれます。

`replication_force_pqc`を有効にした場合も同様です。送信元側が対応していなければ、レプリカは受信できず、レプリケーションが止まります。

つまり、通信の保護を強める変更は、そのまま可用性に影響する変更でもあります。

### 新機能とは別に、既存環境に作用する変更

26.7.0には、新機能を使うかどうかに関係なく、既存環境に作用する変更も含まれます。

- **Enterprise Linux 7への対応の終了**：26.7では、EL7（RHEL 7やOracle Linux 7など）が対応の対象外になりました。EL7で動くサーバは、OSを移行しないと26.7へ進めません。
- **AUTO_INCREMENTの予約**：AUTO_INCREMENTの値を予約する動作を有効にした場合、サーバが異常終了すると、予約したまま使われなかった値が欠番になります。AUTO_INCREMENTは、もともとロールバックなどでも欠番が生じうるものです。それでも、IDが連続することや、最大のIDと件数が一致することを前提にした処理があれば、この条件での影響を確かめてください。

## 7. 自分の見立てを点検する

### 三種類の「確認できた」を区別する

| 確認 | わかること | 根拠になるもの |
|---|---|---|
| 使える | その版・配布物に機能がある | リリースノート、マニュアル |
| 有効にした | 自分の環境でその仕組みが動いている | プラグインの状態、チャネルが選んだ方式、接続で合意した方式 |
| 改善した | 自分の負荷で、応答・遅延・資源の使い方が変わった | 代表的な負荷での比較測定 |

たとえば「26.7にすればレプリカの遅延が減る」という見立てを考えます。原典が支えるのは、一段目の「使える」までです。二段目に進むには、チャネルの前提と方式の選択が必要です。三段目に進むには、自分の負荷での測定が必要です。

チームの計画や報告に含まれる主張が、どの段階まで確認されたものかを区別してください。そうすると、判断の根拠となる範囲がそろいます。

### 比較の条件は、自分のアプリケーションを代表しているか

性能比較を読むときも、自分で測るときも、次の条件が本番と対応しているかを確かめます。

- 接続数と、そのうち同時に実行を要求する数（ピーク時を含む）
- 文の種類と処理時間、長いトランザクションやバッチの有無
- 更新が特定の行やテーブルに集中するかどうか（レプリケーションでの依存関係）
- トランザクションの大きさと、コミット順序を保つ設定の有無
- サーバのCPUとI/O、レプリカで読み取りも処理しているかどうか

たとえば、少数の接続で短い文を流す試験は、多数の接続が同時に実行する状況でのThread Poolの効果を代表しません。また、更新が互いに独立した試験は、特定の行に更新が集中するサービスでのCSAの効果を代表しません。

### 見出しや版の数字から置いた前提を照合する

| 置きがちな前提 | 原典に照らした実際 |
|---|---|
| 最新の更新は全配布物に適用される | 26.7.1は、MySQL ServerのDockerイメージだけが対象 |
| 新機能は既定で有効になる | Thread Poolはプラグインの読み込みが必要。CSAはチャネルごとに明示的に選び、既定はMTA。PQCはTLS 1.3・OpenSSL 3.5.0以降・相手側の対応が必要で、要求は経路ごとの設定 |
| 問題があれば版を戻せばよい | バイナリを旧版に戻す直接のダウングレードは、復旧の前提にできない |

## 8. 更新後のシステム全体を捉える

### 各更新が作用する場所をつなげる

2章の経路に、三つの更新を重ねると次のようになります。

```
アプリケーション
   │ ① 接続の合意 ………………………… PQC（force_pqc）
   ▼
送信元サーバ
   │ ② 要求の実行 ………………………… Thread Pool
   │ ③ コミット・バイナリログ
   ▼
   ④ レプリカから送信元への接続・受信 … PQC（replication_force_pqc）
   ▼
レプリカ
   │ ⑤ 適用・コミット …………………… CSA（チャネルごと）
   ▼
アプリケーションの読み取り（レプリカでも①②が働く）
```

個々の更新は別々の場所に作用しますが、負荷と資源を通じてつながっています。

**書き込みの増加は、レプリカへ伝わります。** たとえば、Thread Poolによって送信元で処理できる書き込みが増えたとします。すると、バイナリログに出る更新も増えます。レプリカの受信と適用がその速さに追いつかなければ、その差が遅延として積み上がり、レプリカから読む内容が古くなります。

書き込んだ直後にレプリカから読む処理があれば、その影響はアプリケーションの振る舞いとして表れます。送信元の処理能力を上げる変更は、レプリカの適用能力と合わせて評価してください。

**読み取りと適用は、同じ資源を使います。** レプリカが読み取りも処理している場合、読み取りの要求とレプリケーションの適用は、同じCPUやI/Oを使います。CSAのワーカーを増やせば、読み取りの応答が遅くなることがあります。逆に、読み取りの並行度が高ければ、適用が遅れて遅延が増えることがあります。それぞれの並行度の設定は、同じ資源をどう配分するかとして決めることになります。

### 観測を、機能の成立と効果に分けて対応させる

| 更新 | 機能が成立しているか | 効果が出ているか |
|---|---|---|
| PQC | 経路ごとの接続の成否、合意したTLSのバージョンと方式 | 接続失敗の件数、接続確立にかかる時間 |
| Thread Pool | プラグインが有効か、実行待ちの状況 | CPUの使用状況、アプリケーション側の応答時間の分布 |
| CSA | チャネルが選んだ適用方式、ワーカーの動作、適用のエラー | 受信と適用の進捗の差、レプリカの遅延 |

レプリケーションの状態は、従来どおり`SHOW REPLICA STATUS`やPerformance Schemaのレプリケーションの表で確認できます。CSAに固有の観測項目は、マニュアルの監視の資料（末尾のS6）にまとまっています。

機能が成立していても、効果が出ているとは限りません。逆に、効果が見えないときは、まず機能が成立しているかを確かめます。たとえば「PQCを要求したら接続が失敗する」「CSAを選んだら適用が止まった」といった状態は、機能の成立の観測で見つけます。

応答時間は、平均だけでなく分布で見てください。Thread Poolでは実行待ちが生じるため、平均は改善しても一部の要求の待ちが長くなることがありえます。

### 更新経路：何を、どの順に、どの方法で更新するか

更新を計画するときは、次の要素を、それぞれの更新経路と利用条件に照らして確認します。

- 現行の版と系列（8.4、9.7など）
- 配布物の種類（パッケージ、Dockerイメージなど）
- OSと、TLSに使うライブラリ（EL7かどうか、OpenSSLの版）
- クライアントのドライバと、そのTLS実装
- 使っているプラグイン
- レプリカの構成（チャネル、ログ形式、GTID、遅延レプリカの有無）

**更新の方法によって、対応する遷移が変わります。** 方法は大きく二つに分かれます。一つは、既存のデータファイルを、新しい版のサーバでそのまま使う方法（インプレース）です。もう一つは、データを別のサーバへ移して切り替える方法です。論理的な移行や、新しい版のレプリカを作って切り替える方法がこちらに含まれます。

二つの方法では、使う手段も互換性の条件も異なります。現行の系列、目的の系列、方法の三つの組み合わせによって、対応する遷移と、経由すべき中間の系列が決まります。たとえば8.4から26.7へ進む場合も、直接の遷移が対応しているのか、9.7などを経由する必要があるのかを、更新経路の表で確かめてください。

**更新の途中では、版の異なるサーバが同時に動きます。** 送信元、レプリカ、クライアントを順に更新すると、途中で版が混在します。その間も、次の二つが成り立つ組み合わせを保つ必要があります。

- レプリカが、送信元の更新ログを受信・適用できる
- クライアントが、新旧どちらのサーバにも接続できる

一般には、レプリカの版が送信元と同じか新しい組み合わせが対応しています。そのため、レプリカを先に更新し、読み取り先を移し、最後に送信元を切り替える順序になります。具体的にどの組み合わせが対応しているかは、マニュアルで確かめてください。

新機能の有効化も、この順序に合わせます。

- `force_pqc`は、すべてのクライアントが対応していることを確かめてから有効にする
- `replication_force_pqc`は、送信元側が対応していることを確かめてから有効にする
- CSAは、レプリカが26.7になり、チャネルの前提がそろってから有効にする

### 回復：どこまで戻せるかは、更新前に決まる

**バックアップの時点と、それ以降の更新を区別します。** バックアップは、ある時点のデータを表します。その時点より後に確定した更新は、バイナリログの適用など、回復の方法が扱える範囲でしか戻せません。

更新後の新しい版で書き込みを受け付けた場合、その書き込みを旧版の回復先へ持っていけるかどうかは、版と方法の組み合わせで決まります。持っていけない場合、バックアップ以降の書き込みは失われるか、別の手段で補う必要があります。そのため、更新後の書き込みをいつから、どのように受け付けるかは、回復の条件として更新前に決めておきます。

**データを戻す条件と、サービスを再開する条件は別です。** バイナリを旧版に戻す直接のダウングレードは、復旧の前提にできません。回復の計画は、更新前のバックアップを基本にします。

そのうえで、次の点を確かめます。

- 回復先の版が、そのデータと、更新後に使った機能を扱えるか
- 別の手段で戻す場合、その版・方法・使った機能の組み合わせが、公式の対応表で許されているか

さらに、データが戻っても、それだけではサービスは再開できません。アプリケーションが回復先に接続でき、読み書きが成立する必要があります。接続の条件には、TLSの設定やドライバの対応も含まれます。

## おわりに

26.7の三つの更新は、要求の処理、更新の適用、接続の確立という別々の場所に作用します。そして、それぞれが設定、構成、接続相手についての条件を持っています。

更新を判断するときは、機能の名前からではなく、次の問いを順に確かめてください。

1. 自分のシステムのどの経路に作用するか
2. その経路で、前提がそろうか
3. 機能の成立と効果を、何で観測するか
4. うまくいかなかったとき、どこまで戻せるか
