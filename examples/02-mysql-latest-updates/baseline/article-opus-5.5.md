# MySQL最新アップデートの紹介(2026年10月版):エンジニアリーダーが今押さえるべきこと

> **対象読者**:MySQLを使うプロダクトのテックリード、EM、SRE/DBAリード
> **注記**:本記事は公式ドキュメントと公開済みのリリース方針をもとに整理しています。パッチ番号やクラウド各社のサポート期限は随時更新されます。最終判断の前に一次情報を確認してください。

## TL;DR

- **MySQL 8.0は2026年4月にEOLを迎えました。** 本番に8.0が残っているなら、今四半期の最優先事項はアップグレード計画です。
- **本番環境の標準はLTS(8.4、および後継の9.7系)です。** 四半期ごとに出るInnovationリリースは、検証や先行評価に使います。
- **8.4は「デフォルトが変わったリリース」です。** 認証方式、レプリケーション用語、InnoDBの設定値が変わり、既存アプリや運用スクリプトに影響します。
- **新機能はエディションによる差が大きくなっています。** ベクトル型やJavaScriptストアドなどは、Community/Enterprise/HeatWaveのどれで使えるかを前提に技術選定する必要があります。

---

## 1. リリースモデル:LTSとInnovation

2023年(8.0.34)以降、MySQLは「LTS」と「Innovation」の2系統でリリースされています。

| 種別 | 該当バージョン | リリース間隔 | サポート | 変更の性質 | 想定用途 |
|---|---|---|---|---|---|
| LTS | 8.4、9.7系 | 約2年ごと | 長期(8.4はPremier 2029年4月、Extended 2032年4月まで) | パッチはバグ修正とセキュリティ修正が中心。機能削除はない | 本番 |
| Innovation | 9.x系の各リリース | 四半期ごと | 次のInnovationが出るまで | 新機能の追加、非推奨機能の削除がある | 検証、先行評価、短いサイクルで追従できる環境 |

リーダーとして押さえるべき点は次の3つです。

- **Innovationを本番で使うと、3か月ごとにメジャー相当のアップグレードが必要になります。** チームの運用体力と見合うかを判断してください。
- **LTSのパッチは四半期ごとに出ます。** OracleのCritical Patch Update(1・4・7・10月)と同じタイミングです。パッチ適用を「イベント」ではなく「定常運用」として組み込みます。
- **アップグレード経路を確認してください。** 8.0から8.4への直接アップグレードは公式にサポートされています。8.4からはLTS系列内でのダウングレードもサポートされますが、**8.4から8.0には戻せません**。LTSを飛び越える経路を取る場合は、公式のアップグレードパスを必ず確認してください。

## 2. 8.0 EOLが意味すること

- **セキュリティ修正が提供されなくなります。** 脆弱性診断や監査(PCI DSS、ISMSなど)で指摘される対象になります。
- **マネージドサービスでは延長サポートが有償になります。** たとえばAmazon RDS for MySQL 8.0は、2026年7月末で標準サポート終了と案内されています。それ以降は有償の延長サポートが適用されます。Aurora MySQLなどは独自のライフサイクルを持つため、サービスごとに確認してください。
- **延長サポート費用は「移行を先送りするコスト」です。** 移行工数の見積もりと並べて予算化すると、経営層への説明が通りやすくなります。

## 3. 8.4 LTSへの移行でつまずきやすい変更

### 3.1 認証:`mysql_native_password` からの脱却

- 8.4では `mysql_native_password` が**デフォルトで無効**です。一時的に有効化することはできます。
- 9.0以降では**完全に削除**されています。9.7 LTSへ進む前提なら、8.4への移行時点で解消しておくべきです。
- `caching_sha2_password` に対応していない古いドライバー、コネクションプール、プロキシが残っていないかを確認します。

```sql
-- 旧方式のユーザーを洗い出す
SELECT user, host FROM mysql.user WHERE plugin = 'mysql_native_password';

-- 新方式へ切り替える
ALTER USER 'app'@'%' IDENTIFIED WITH caching_sha2_password BY '********';
```

### 3.2 レプリケーション関連の旧構文の削除

8.4では、MASTER/SLAVEを含む旧構文が削除されました。監視スクリプト、Runbook、構成管理コード、古いExporterに影響します。

| 削除された構文 | 置き換え先 |
|---|---|
| `CHANGE MASTER TO` | `CHANGE REPLICATION SOURCE TO` |
| `START SLAVE` / `STOP SLAVE` | `START REPLICA` / `STOP REPLICA` |
| `SHOW SLAVE STATUS` | `SHOW REPLICA STATUS` |
| `SHOW MASTER STATUS` | `SHOW BINARY LOG STATUS` |
| `RESET MASTER` | `RESET BINARY LOGS AND GTIDS` |

### 3.3 InnoDBのデフォルト値の変更

8.4では、SSDと現代的なハードウェアを前提にデフォルト値が見直されました。

| パラメータ | 8.0 | 8.4 |
|---|---|---|
| `innodb_adaptive_hash_index` | ON | OFF |
| `innodb_change_buffering` | all | none |
| `innodb_io_capacity` | 200 | 10000 |
| `innodb_log_buffer_size` | 16MB | 64MB |
| `innodb_flush_method`(Linux) | fsync | O_DIRECT(対応環境) |

`my.cnf` で明示的に指定していないパラメータは、アップグレードすると挙動が変わります。とくにAdaptive Hash Indexが無効になる影響はワークロードによって差が出ます。本番相当の負荷で性能を比較してください。

### 3.4 その他の削除・変更

- **`mysqlpump` の削除**:MySQL Shellのdump/loadユーティリティか、`mysqldump` に移行します。
- **keyringプラグインの削除**:`keyring_file` などのプラグインは削除されました。コンポーネント方式に移行します。
- **外部キー制約の制限**:一意でないキーや部分キーを参照する外部キーは、デフォルトで作成できなくなりました(`restrict_fk_on_non_standard_key`)。
- **Group Replicationのデフォルト変更**:`group_replication_consistency` は `BEFORE_ON_PRIMARY_FAILOVER` に、`group_replication_exit_state_action` は `OFFLINE_MODE` に変わりました。
- **`binlog_transaction_dependency_tracking` の削除**:WRITESETベースの依存関係追跡が常に使われます。

これらはMySQL Shellのアップグレードチェッカーで大半を検出できます。

```js
// 移行先と同じバージョンのMySQL Shellで実行する
util.checkForServerUpgrade('admin@db-primary:3306', {outputFormat: 'JSON'})
```

## 4. 注目すべき新機能

### 8.4 LTSで使えるもの

- **ヒストグラムの自動更新**:`ANALYZE TABLE ... UPDATE HISTOGRAM ... AUTO UPDATE` を指定すると、統計情報の鮮度を保ちやすくなります。
- **GTIDタグ**:GTIDにタグを付けられるようになり、トランザクションの由来(バッチ処理、メンテナンス作業など)を識別しやすくなりました。
- **MySQL Routerの読み書き分離**:InnoDB Cluster構成では、アプリ側を改修しなくても参照系クエリをセカンダリへ振り分けられます。
- **LTS系列内でのクローンとダウングレード**:パッチバージョンが異なるサーバー間でもクローンでき、パッチ適用時に切り戻せます。

### 9.x系で入ったもの(LTSとしては9.7系で提供)

- **VECTOR型**:埋め込みベクトルを保存できます。ただしCommunity Editionで使えるのは型と変換関数が中心です。距離計算やベクトル検索を本格的に使うにはHeatWave側の機能が必要です。
- **JavaScriptストアドプログラム**:ストアドプロシージャや関数をJavaScriptで書けます。Enterprise/HeatWave向けの機能です。
- **実行計画の機械可読化**:`EXPLAIN` や `EXPLAIN ANALYZE` のJSON出力が強化され、結果を変数に格納できるようになりました。実行計画の自動収集や回帰検知に組み込みやすくなっています。

## 5. エディションと提供形態の選択

新機能の多くは、Communityでは使えないか、使える範囲が限られています。

| 提供形態 | 特徴 | 留意点 |
|---|---|---|
| Community | 無償、移植性が高い | ベクトル検索やJavaScriptストアドは対象外か限定的 |
| Enterprise | 監査、ファイアウォール、Thread Pool、Enterprise Backup、JavaScriptストアドなど | ライセンス費用がかかる。Oracleとの契約が前提 |
| HeatWave(OCI/AWS/Azure) | インメモリ分析、Lakehouse、AutoML、ベクトルストア | 機能を使い込むほど移植性が下がる |
| 他社マネージド(RDS、Aurora、Cloud SQL など) | 運用負荷が低い | LTS中心の提供が多く、Innovationへの対応は限定的なことが多い |

**判断の軸**は、「Communityで動くことを前提にした設計を保つのか」と「特定エディションの機能に意図的に寄せるのか」を明示することです。暗黙のうちに限定機能を使い始めると、後でロックインや移植性の問題として表面化します。たとえばRAGなどのベクトル検索用途では、MySQLに寄せるか、専用のベクトルDBや他のエンジンを使うかを、アーキテクチャ判断として記録しておくことを推奨します。

## 6. リーダー向けアクションプラン(今後90日)

| 時期 | アクション | 成果物 |
|---|---|---|
| 1〜2週目 | 全DBのバージョン、エディション、ホスティング形態、接続ドライバー、運用ツールを棚卸しする | DBインベントリ、8.0残存リスト |
| 3〜4週目 | 移行先を決める(8.4か9.7か)。アップグレードチェッカーを実行する | バージョン方針、互換性課題の一覧 |
| 5〜8週目 | ステージングで検証する(認証方式、旧構文、性能)。`pt-upgrade` などでクエリ結果と性能を比較する | 検証レポート、修正チケット |
| 9〜12週目 | レプリカから順に移行し、切り替える。Blue/Green構成で切り戻し期間を確保する | 移行完了、旧環境の廃止計画 |

**バージョン方針についての推奨**:8.0から今すぐ移行する場合は、**8.4 LTSを第一候補**にしてください。周辺ツールやマネージドサービスの対応が成熟しており、Premier Supportも2029年まで続きます。9.7系は、ベクトル型など9.x系の機能が必要な場合や、利用するクラウドの対応状況を確認できた場合に選びます。どちらを選ぶ場合でも、`mysql_native_password` と旧レプリケーション構文はこのタイミングで解消しておくと、次のLTS移行が軽くなります。

**切り戻し設計**:8.4から8.0へはダウングレードできません。旧環境を一定期間残すBlue/Green構成か、論理バックアップから復元する手順を、移行計画に必ず含めてください。

---

## 7. まとめ

- 8.0のEOLは過ぎています。移行コストと延長サポート費用を並べ、今期中に意思決定してください。
- 本番はLTSで運用し、四半期ごとのパッチ適用を定常業務にします。Innovationは検証に使います。
- 8.4はデフォルト値と構文が変わるリリースです。アップグレードチェッカーと本番相当の検証で事前に潰してください。
- 新機能はエディションによる差が大きいため、「どこまで特定エディションに寄せるか」をアーキテクチャ判断として明文化してください。

MySQLは「一度入れたら長く放置できるDB」から「定期的に更新する前提のDB」へ変わりました。バージョン管理を属人的な作業から、チームの運用プロセスへ移すことが、リーダーとして取り組むべき本質的な課題です。
