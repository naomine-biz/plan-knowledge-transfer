## 2-2. 既知の内容から到達目標へ進む経路

1. **版と提供範囲 → G1**  
   既存MySQLの利用経験 → A1のリリースモデル → A2の版の読み方 → A3の版・配布状態 → F3で提供範囲の推測を点検。最新機能の紹介対象と、自社の更新先を同じものと決め付けない経路がある。

2. **要求処理 → G2 → G3**  
   既知の接続・トランザクション → A4 → B1の接続ごとのスレッド・競合 → B2のサーバ側Thread Poolと接続再利用の役割の違い → B3の提供・有効化 → E1の負荷条件 → F1・F2 → H1.1・H1.2の更新流量・資源共有 → H2.1の待ち・資源・応答の観測。機能の仕組みから、全体への影響と確認へ進める。

3. **更新の適用 → G2 → G3**  
   既知のトランザクション・レプリカの用途 → A4・C1 → C1.1のチャネル → C2のGTID・行ベース → C2.1の自動位置決定。続いてC3.1で依存・適用完了・コミット可能を区別し、C3の設定条件の下でC3.2の従来方式との差を捉える → C4・C5の選択・資源・利用条件 → E2・E3 → F1・F2 → H1.1・H1.2・H2.1。GTIDという識別の役割と、並行化を制約する依存の役割を混同せずに追える。

4. **通信 → G2 → G3**  
   既知の接続 → D1のTLSでの合意 → D2.1のPQCの目的・保護対象とD2.2のOpenSSLの役割 → D2の対応する版・TLS条件 → D3・D3.1の要求、相手側、合意結果、通信経路 → E4の不成立条件 → F1 → H2.1の接続・合意方式の観測とH3の更新時の照合。TLS内部や暗号ライブラリを開始時の既知へ追加する必要はない。

5. **更新・回復 → G3**  
   G1の対象版・配布範囲とG2の利用条件 → E5の既存環境への変更 → F3で更新・復旧の期待を点検 → H3.1の系列と方法による遷移 → H3.2の混在期間の成立条件 → H4.1のバックアップ時点・以後の更新・回復方法 → H4.2の回復先でのデータ利用とサービス再開。戻せるデータと、アプリケーションが再開できる条件を結び付けられる。

追加された子項目は親項目で獲得する理解の分解として読める。たとえばD2.1・D2.2をD2の前提として使い、C3.1・C3.2をC3の条件の下で結び付ける。識別子の表示順だけから、前提の欠落とは判定しない。

全体はLv2の仕組み、Lv3の成立範囲、Lv4の期待と根拠の点検、Lv5の全体の関係へ進む。H3・H4は前段で得た版・利用条件・根拠の点検を使い、G3の更新と回復を具体化している。
