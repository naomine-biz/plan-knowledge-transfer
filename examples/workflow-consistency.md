# READMEの使い方と実際の工程の照合

対象は[リポジトリのREADME](../README.md)、[スキルの手順](../SKILL.md)、[サンプルのREADME](README.md)。
計画作成時のスキルはcommit `e62e437`。2026-10-08にHumanが二つの計画を承認した後、別工程で記事を生成した。

## 計画が完成するまで

| READMEとスキルにある工程 | 実際に行ったこと | 保存した証拠 |
|---|---|---|
| スキルを読み、テーマ・想定読者・目的を整理する | 二つのテーマを別々の計画にした。テーマと職位は依頼から取得し、追加の読者前提は仮定と明記した。 | 各`plan.md`の「承認用の要約」「目的・前提と到達目標」 |
| 読者に応じてLv5かLv6を選ぶ | CTOはLv6、エンジニアリーダーはLv5とした。読者の役割から目標を選べたため、目標を決める追加質問は不要だった。 | 各計画の目標とG1〜G3 |
| 世界知識から全体像を捉え、必要な理解を分解する | 業務要求・データモデル・伝播・回復・資源配分、または要求処理・更新適用・通信・更新と回復の関係を整理した。 | [NoSQL初版](01-nosql-rdbms-strategy/plan-v1.md)、[MySQL初版](02-mysql-latest-updates/plan-v1.md) |
| 全体像を捉えられない題材は、リサーチ後にHumanへ確認する | 今回は両題材の全体像を組み立てられたため、この分岐は適用しなかった。MySQLの最新仕様は個別の事実確認で扱った。 | 各計画の世界知識からの整理と、確認した事実の区別 |
| 重要な成立条件や最新情報を資料へ照合する | NoSQLの分類から保証を推測しないための機能例と、MySQLのリリース日・提供範囲・機能の条件を公式資料で確認した。自社性能や移行成功の実測は行っていない。 | 各計画の出典S1以降と、未提示・未実証事項 |
| 到達目標から必要な理解・前提・順序をそろえる | 理解項目にIDと前提を置き、Lv2から目標までの順序を示した。本文、図表配置、文章量の指定は加えていない。 | 各計画の理解項目と順序 |
| 読者ペルソナで理解経路と不足を点検する | 作者の文脈を持たない読者役へ、計画・読者条件・点検手順を渡した。各テーマ6件の不足を、計画担当が必要な理解として採用した。 | [NoSQL初回点検](01-nosql-rdbms-strategy/reader-review-v1.md)、[MySQL初回点検](02-mysql-latest-updates/reader-review-v1.md)、各`review-resolution.md` |
| 指摘を照合し、修正のつながりと止めどころを確認する | 修正版を同じ読者役へ渡した。新たな必須の不足は指摘されず、計画担当が注記と根拠を照合し、分解終了の理由を記録した。 | 各`plan-v2-reviewed.md`、`reader-review-v2.md`、最新`plan.md` |
| 要約と詳細を提示してHumanの承認を得る | 完成条件を確認したv2を承認待ちとして提示し、「両方とも承認します。」という回答を得た。 | [承認記録](approval.md) |
| 承認状態を記録し、計画を成果物として終了する | 承認後は`plan.md`の承認情報だけを変更した。初版と再点検に渡した版には、当時の状態を残した。 | 各`plan.md`、`plan-v1.md`、`plan-v2-reviewed.md` |

## 承認済み計画を使った記事サンプル

READMEは、完成した計画を執筆時の内容・順序選択の基準として使えると説明している。記事サンプルは、その用途を別工程で試したもの。

| サンプルのREADMEにある工程 | 実際の実行と証拠 |
|---|---|
| 承認後に執筆する | [承認記録](approval.md)の回答後に2本のCLI実行を開始した。実行日時は各`run.json`。 |
| 完成した計画と短い依頼文を渡す | 各`input.md`は、`prompt.md`、空行、承認済み`plan.md`を連結した全入力。連結結果と保存した入力をバイト単位で照合した。 |
| Opus 5.5を使う | 指定モデルは`claude-opus-5-5`。CLI結果の`modelUsage`と`canonicalModel`を確認し、各`run.json`へ記録した。 |
| 執筆条件を固定して記録する | 新規セッションで各1回、同じCLIオプションを指定した。実行条件、CLIバージョン、入力のハッシュを各`run.json`へ保存した。 |
| 生成された記事を保存する | CLI結果の`result`をそのまま`article-opus-5.5.md`へ保存し、返された文字列との一致と出力のハッシュを確認した。 |
| 生成経緯を追えるようにする | 初版、点検に渡した版、2回の読者応答、指摘の採否、Human承認、入力、記事、実行記録を同じサンプル集へ保存した。 |

## 照合結果

二つの計画の作成から承認までの工程は、READMEとスキルの手順に対応している。記事の生成は、計画のタスクを終了した後に実行した。
読者ペルソナによる計画の点検、原典による事実確認、Humanによる承認は、それぞれの記録で確認できる。

この照合で確認したのは、工程と保存した成果物の対応である。仮想の読者の応答から、実際の読者の理解を実証したとは扱わない。記事への追加の執筆・校正工程は実行していない。

## ファイルの照合

- 両実行の成功、指定モデルと実行モデルの一致を確認した。
- 依頼文と承認済み計画の連結が`input.md`と一致し、記事がCLIの返した`result`と一致することを、バイト単位で確認した。
- `run.json`にある依頼文・計画・入力・記事のSHA-256と、保存した各ファイルが一致した。初版と再点検に渡した版のハッシュも、点検時の記録と一致した。
- Markdown 27ファイル中のローカルファイルリンク70件の参照先を確認した。
- 通常の`git diff --cached --check`が報告した行末空白は、Markdownの改行用の2スペースだった。改行用の2スペースを個別に照合し、原稿と入力の同一性を保つためそのまま保存した。その他の差分は、`git -c core.whitespace=-blank-at-eol diff --cached --check`で確認した。
