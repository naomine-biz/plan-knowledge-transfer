# CTOのための「NoSQLとRDBMSの使い分け戦略」:技術選定を経営判断として捉える

データベースの選定は、一度決めると数年単位で組織を縛る技術判断です。アプリケーションコードは書き換えられます。しかし蓄積されたデータと、それに依存する業務・分析・運用体制は簡単には移せません。

それでも「NoSQLかRDBMSか」という議論は、性能やスケーラビリティといった単一の軸や、エンジニアの好みで語られがちです。本記事ではCTOの立場から、この選択を次の2つの観点で整理し、実務で使える判断の枠組みを示します。

- どこに複雑さを置くか
- 間違えたときに何を失うか

---

## 1. 前提:二項対立はもう成り立たない

### NoSQLは一つのカテゴリではない

「NoSQL」は「RDBMSではないもの」の総称にすぎません。中身は性質のまったく異なるデータストアの集合です。

| 分類 | 代表例 | 得意領域 |
|---|---|---|
| キーバリュー | Redis、Amazon DynamoDB | セッション、キャッシュ、キー指定の高速な読み書き |
| ドキュメント | MongoDB、Firestore | 階層構造を持つ可変なデータ、集約単位での読み書き |
| ワイドカラム | Apache Cassandra、ScyllaDB、Bigtable | 大量の書き込み、時系列データ、地理分散 |
| グラフ | Neo4j、Amazon Neptune | 多段の関係探索 |
| 検索エンジン | Elasticsearch、OpenSearch | 全文検索、ファセット検索、ログ分析 |
| 特化型 | 時系列DB、ベクトルDB | 特定のワークロードへの最適化 |

「NoSQLを採用するか」という問いは粒度が粗すぎます。問うべきは「どの種類の、どの製品を、どの用途に使うか」です。

### 境界線は年々曖昧になっている

RDBMSはNoSQLの領域に踏み込んでいます。

- PostgreSQLのJSONB型やMySQLのJSON型で、スキーマの柔軟なデータを扱える
- 全文検索やベクトル検索(pgvectorなど)も拡張機能で実現できる
- 分散SQL(Google Cloud Spanner、CockroachDB、TiDB、YugabyteDB、Amazon Aurora DSQLなど)が、SQLと強い整合性を保ったまま水平スケールを実現している

逆方向の動きもあります。MongoDBは4.0以降で複数ドキュメントにまたがるトランザクションをサポートし、DynamoDBもトランザクションAPIを提供しています。

したがって本当に問うべきは「NoSQLかRDBMSか」ではありません。次の問いです。

> このデータは、どのような整合性で、どのようなアクセスパターンで読み書きされ、誰が運用するのか。

## 2. 基本姿勢:「デフォルトはRDBMS、例外に理由を求める」

筆者が推奨する基本姿勢は、RDBMSを既定の選択肢とし、それ以外を選ぶときに明確な理由を求めることです。これはRDBMSが常に優れているという意味ではありません。立証責任をどちらに置くかという話です。

### 理由1:未来のクエリに強い

正規化されたリレーショナルデータは、設計時に想定していなかった問いにもSQLで答えられます。新機能、経営分析、監査対応、障害調査などです。

一方、DynamoDBに代表されるキーバリュー型の設計は、アクセスパターンを先に決めてからデータ構造を決めます。新しいアクセスパターンが必要になると、インデックスの追加やデータの再設計・再投入が必要になります。

事業の初期ほど、将来のクエリは予測できません。

### 理由2:整合性をデータベースに任せられる

一意制約、外部キー、トランザクションをデータベースが保証してくれれば、アプリケーションはその前提の上に書けます。

整合性をアプリケーション側で担保するコードはバグの温床です。しかもコードレビューで検出しにくく、問題が発覚するのは不整合なデータが蓄積した後です。

### 理由3:人材と知見の厚み

SQLとリレーショナルモデリングを扱えるエンジニアは採用市場に多くいます。さらにSQLはエンジニア以外にも開かれています。アナリスト、プロダクトマネージャー、カスタマーサポートが自分でデータを確認できることは、組織全体の意思決定速度に直結します。

### 理由4:単一ノードの限界は想像より遠い

近年のマネージドRDBMSは、大容量メモリと高速ストレージを備えたインスタンスを選べます。リードレプリカやキャッシュと組み合わせれば、多くのサービスはRDBMSの限界に到達する前に別の課題(組織の拡大、プロダクトの方向転換)に直面します。

「将来のスケールのために最初からNoSQL」という判断は、多くの場合、早すぎる最適化です。

### 「スキーマレスだから開発が速い」という誤解

ドキュメントDBを選ぶ理由として「スキーマレスで開発が速い」がよく挙げられます。しかしスキーマは消えるわけではありません。データベースからアプリケーションコードへ、暗黙的に移るだけです。

複数のサービスや複数世代のコードが同じデータを読むようになると、どこにも明文化されていないスキーマは技術的負債になります。スキーマの柔軟性が必要なら、まずRDBMSのJSON型で足りるかを検討する価値があります。

## 3. NoSQLを選ぶべき明確なシグナル

NoSQLの本質的な強みは、「クエリの自由度という制約を受け入れる代わりに得られる、予測可能な性能とスケール特性」にあります。

たとえばDynamoDBが規模によらず安定した低レイテンシを提供できるのは、高コストなクエリをそもそも書けない設計になっているからです。この制約がビジネス要件と合致するときが、NoSQLを選ぶべきときです。

| シグナル | 具体例 | 選択肢の例 |
|---|---|---|
| アクセスパターンが単純かつ既知で、規模が極めて大きい | ユーザー設定、カート、デバイス状態 | DynamoDB、Cassandra |
| 揮発的なデータで、低レイテンシが必須 | セッション、レート制限、リアルタイムランキング | Redis |
| 書き込みが圧倒的に多く、追記が中心 | IoTテレメトリ、行動ログ、イベントストリーム | ワイドカラム型、時系列DB |
| 全文検索・あいまい検索・関連度順の並べ替え | 商品検索、ログ検索 | Elasticsearch、OpenSearch |
| 多段の関係を辿る探索 | 不正検知、レコメンド、権限グラフ | グラフDB |
| 複数リージョンでの書き込みと高可用性 | グローバル展開するサービス | DynamoDB Global Tables、Cassandra、分散SQL |
| 集約単位で読み書きされ、構造が頻繁に変わる | CMS、商品ごとに属性が異なるカタログ | ドキュメントDB(JSON型も比較検討) |

複数リージョンや大規模スケールの要件があっても、それだけでNoSQLとは限りません。分散SQLという選択肢があるためです。ただし分散SQLにも、分散トランザクションによるレイテンシの増加や、単一ノードのRDBMSとは異なる性能特性があります。そのまま置き換えられるものではない点に注意が必要です。

## 4. 見落とされがちな総保有コスト

技術選定の議論は、導入時の性能や開発体験に偏りがちです。CTOが見るべきは、数年単位での総保有コストです。

### 4.1 アクセスパターン先行設計の変更コスト

アクセスパターンを前提にデータを非正規化して配置する設計は、要件が安定していれば非常に効率的です。しかし事業の方向転換や新機能で前提が崩れると、データの再設計と全件移行が必要になります。これは数週間から数か月単位のプロジェクトになり得ます。

### 4.2 整合性をアプリケーションで担う開発コスト

次のような課題を、アプリケーションエンジニアが恒常的に意識し続ける必要があります。

- 結果整合性を前提とした画面設計
- 非正規化データの更新漏れ
- リトライ時の冪等性の担保

これはチームの認知負荷として、開発速度に静かに効いてきます。

### 4.3 分析基盤の別途構築

アドホックな集計に向かないデータストアを選んだ場合、分析のためにはデータウェアハウスへのパイプラインが別途必要になります。RDBMSでも規模が大きくなれば同様の構築は必要です。違いは、その必要が「最初の分析要望の時点」で発生することです。

### 4.4 データストアを追加するたびに発生する「運用税」

新しい種類のデータストアを一つ追加するたびに、次の仕事が増えます。

- バックアップとリストア訓練
- 監視とアラート設計
- オンコール対応
- バージョンアップとセキュリティパッチ
- アクセス制御と監査ログ
- 障害復旧(DR)計画
- コスト監視

マネージドサービスはこの負担を軽減しますが、ゼロにはしません。運用負荷はおおむね「データストアの種類の数 × 環境の数 × 必要な専門知識」で増えていきます。

### 4.5 課金モデルの違い

リクエスト課金型のサービスは、低トラフィック時には非常に安価です。一方、トラフィックの急増や非効率なアクセス(全件スキャンなど)でコストが跳ね上がることがあります。インスタンス課金型は、使用率が低くても固定費がかかる代わりに、コストを予測しやすくなります。

どちらが有利かはワークロード次第です。少なくとも選定時に、想定トラフィックでの月額試算は必ず行うべきです。

## 5. 組み合わせるときの原則:正となるデータストアを一つに決める

複数のデータストアを用途に応じて使い分ける「ポリグロット・パーシステンス」は、規模が大きくなれば自然な姿です。ただし無秩序に組み合わせると、データ不整合と運用負荷の温床になります。次の4原則を守ることを推奨します。

### 原則1:データごとに、正となるデータストアを一つ決める

各データについて、どのデータストアが正(System of Record)なのかを明確にします。それ以外のストアにあるデータは、すべて正から派生したものと位置づけます。

### 原則2:二重書き込みを避ける

アプリケーションがRDBMSと検索エンジンの両方に直接書き込む設計は、片方だけが失敗したときに不整合を生みます。次のいずれかの仕組みで、正から非同期に伝播させてください。

- **Transactional Outbox パターン**:業務データの更新と同じトランザクションで送信用のイベントを記録し、別プロセスが配信する
- **CDC(Change Data Capture)**:Debeziumなどでデータベースの変更ログを取り出して配信する

### 原則3:派生ストアは再構築可能にする

検索インデックスやキャッシュが壊れても、正から再生成できる状態を保ちます。そうすれば、派生ストアの技術選定は「後からやり直せる判断」になります。

### 原則4:データアクセスを境界の内側に閉じ込める

データストアへのアクセスは、リポジトリ層やサービス境界の内側に閉じ込めます。データストア固有のAPIがコードベース全体に散らばると、将来の移行コストが跳ね上がります。

### 典型的な構成

```
[アプリケーション] ──参照──▶ [キャッシュ (Redis)]
     │
     │ 書き込み(トランザクション)
     ▼
[RDBMS:正となるデータストア]
     │
     └─ CDC / Outbox ─┬─▶ [検索エンジン]
                      ├─▶ [データウェアハウス / 分析基盤]
                      └─▶ [他サービスへのイベント配信]
```

## 6. 事業フェーズ別の戦略

### 初期(プロダクトマーケットフィット前)

単一のマネージドRDBMSを中心に据えます。必要に応じてRedisを加える程度に留めるのが合理的です。この時期に最も重要なのは変更の速さであり、アクセスパターンはまだ定まっていません。スキーマの柔軟性が必要な部分はJSON型で吸収します。

### 成長期

ボトルネックが計測によって明らかになった箇所から、順に切り出していきます。

- 読み込み負荷 → リードレプリカやキャッシュ
- 検索要件 → 検索エンジン
- 重い処理 → 非同期キュー
- 分析要望 → CDCによるデータウェアハウスへの連携

重要なのは、推測ではなく計測に基づいて判断することです。

### 大規模期

特定のドメインで、NoSQLや分散SQLの採用を検討する段階です。このとき「全社でNoSQLへ移行する」といった一律の判断は避けます。ドメインごとに、要件が明確な部分から適用します。この段階では、プラットフォームチームが標準構成を整備し、各チームが迷わず使える状態を作ることが重要になります。

## 7. 意思決定フレームワーク

### 選定時に答えるべき7つの問い

1. **整合性**:複数のエンティティにまたがる更新は不可分である必要があるか。不整合が起きたときのビジネス影響はどの程度か。
2. **アクセスパターン**:読み書きのパターンは既知で、今後も安定していると言えるか。
3. **スケール**:想定する規模は、RDBMSで現実的に対応できる範囲を超えるか。根拠となる数値はあるか。
4. **クエリの多様性**:管理画面、分析、アドホックな調査はどの程度必要か。
5. **運用体制**:そのデータストアを障害時に復旧できるメンバーが、少なくとも2名いるか。
6. **コスト**:想定トラフィックでの月額試算と、トラフィックが10倍になったときの試算はどうなるか。
7. **撤退**:選定が誤りだった場合、どのように、どの程度のコストで移行できるか。

### 「やり直せる判断」と「やり直せない判断」を分ける

Amazonが提唱する「One-way door(後戻りできない扉)/ Two-way door(後戻りできる扉)」の考え方は、データベース選定にもそのまま当てはまります。

- **Two-way door**:キャッシュや検索インデックスなど、再構築可能な派生ストア。現場の裁量で軽く判断してよい。
- **One-way door**:正となるデータストアの選定。CTOを含めたレビューを経て、慎重に判断すべき。

### 判断をADRとして記録する

選定理由はArchitecture Decision Record(ADR)として残します。最低限、次の項目を含めます。

- 背景と要件
- 検討した選択肢
- 選定理由
- 受け入れるトレードオフ
- 撤退の条件と方法
- 運用責任者

数年後に「なぜこれを使っているのか」を誰も説明できない状態こそが、最も高くつきます。

## 8. 組織とガバナンス

### 承認済みデータストアの一覧を持つ

社内で標準として運用ノウハウを蓄積しているデータストアを明示します。それ以外を導入する場合には、明確な審査を経る仕組みにします。

### 新規導入の受け入れ基準を定める

たとえば次のような基準です。

- 運用可能なメンバーが複数いる
- バックアップとリストアの手順が検証済みである
- 監視とアラートが整備されている
- オンコール体制に組み込まれている
- 撤退計画がある

### 属人化を防ぐ

特定のエンジニアの強い推薦で導入されたデータストアが、その人の退職後にブラックボックス化するのは、よくある失敗です。技術選定の権限と運用責任は、セットで割り当ててください。

### 標準構成を整備する

プラットフォームチームが、標準的なデータストアの構築テンプレート、監視設定、接続ライブラリを提供します。正しい選択が最も楽な選択になる状態を作ることが、ガバナンスを形骸化させない鍵です。

## 9. 2026年時点の潮流

### PostgreSQLの存在感の拡大

PostgreSQLは豊富な拡張機能のエコシステムを持ちます。地理情報のPostGIS、時系列のTimescaleDB、ベクトル検索のpgvectorなどです。そのため、多くの用途を一つのエンジンで賄うという選択肢が現実的になっています。

「まずPostgreSQLで足りるか」を最初に問うのは合理的な出発点です。ただし拡張機能にも、規模が大きくなったときの性能限界があります。専用製品との比較検討は省略すべきではありません。

### 分散SQLの成熟

水平スケールの選択肢はもはやNoSQLだけではありません。強い整合性とSQLを維持したまま、スケールできる選択肢が広がっています。

### ベクトル検索の汎用データベースへの取り込み

生成AIの活用拡大に伴い、ベクトル検索の需要が急増しています。専用のベクトルDBに加え、既存のデータベースや検索エンジンがベクトル検索機能を提供するようになりました(pgvector、OpenSearch、MongoDB Atlas Vector Searchなど)。

データ規模が中程度であれば、既存のデータストアに統合して運用負荷を抑えるほうが合理的なケースが多くなっています。

### サーバーレス化と従量課金の普及

運用負荷は下がり続けています。その分、判断の重心は次の点に移っています。

- コストの予測可能性
- ベンダーロックインをどこまで許容するか

## まとめ

- **「NoSQLかRDBMSか」ではなく、データごとに整合性・アクセスパターン・運用体制を問う。** NoSQLは一枚岩ではなく、RDBMSとの境界も曖昧になっている。
- **デフォルトはRDBMS、例外には理由を求める。** 未来のクエリへの対応力、整合性の保証、人材の厚みは、特に事業初期において大きな価値を持つ。
- **NoSQLは、制約と引き換えに予測可能な性能とスケールを得る技術である。** その制約が要件と合致するときに選ぶ。
- **組み合わせるなら、正となるデータストアを一つに決め、派生データは再構築可能にする。** 二重書き込みは避け、OutboxやCDCで伝播させる。
- **データストアの種類を増やすたびに運用税がかかる。** 導入基準と撤退計画をガバナンスとして組み込む。

CTOが選ぶべきは、ベンチマーク上で最速のデータベースではありません。組織が責任を持って運用し続けられ、事業の変化に追従できるデータベースです。技術選定を、エンジニアリング組織の持続可能性に対する投資判断として捉えることが、使い分け戦略の本質です。
