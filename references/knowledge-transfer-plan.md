# 知識移転を計画する

テーマと想定読者から、執筆目的を満たすために読者が獲得すべき理解を計画する。
目標レベルと理解を積み上げる順序は[thinking-levels.md](thinking-levels.md)に従う。

## 1. 執筆目的と到達目標をそろえる

依頼と既存の文脈から、テーマ、想定読者、読者の前提知識、執筆目的、文書が答える問い、扱う範囲を確認する。
目標レベルが不明な場合はHumanに確認する。
その他の未指定事項は、計画に仮定と影響を示す。目的や到達目標の成立に関わる前提が不明な場合は確認する。

計画担当は対象を目標レベルで捉え、全体の関係と成立条件を整理する。その理解を基に、読者が最終的に何を理解し、どの判断ができるようになるべきかを到達目標として定める。
到達目標には、テーマ固有の要素・関係・条件・判断を明記する。「テーマを理解する」「全体を説明できる」だけでは、理解の対象を特定できない。

複数の独立したテーマを扱う場合は、単位ごとに到達目標を設計し、共通の読者条件と、単位間で必要な前提を示す。

## 2. 到達目標を理解の項目へ分解する

計画の中心は、各説明を読むことで読者に達成してもらうことを列挙した、理解の項目である。
到達目標から必要な理解を洗い出し、複数の関係を含む項目は子項目へ分ける。親子関係と、前提として使う項目の関係を示す。

### 各項目に書くこと

- **達成する理解**：読者が理解すべき具体的な因果、要素の役割と関係、成立条件、適用範囲、区別、全体の動作や判断。
- **必要とする理解**：その項目に先立って必要な項目、または読者が既に知っていると仮定した内容。
- **目的へのつながり**：親項目や到達目標の、どの理解を支えるか。階層で明らかな場合は、その関係を使う。

番号や短い識別子を付け、項目間の関係を参照できるようにする。文章量や項目数に固定の目安を設けない。
項目は「何を伝え、その結果、何を理解してもらうか」で書く。関係・条件・判断の対象を具体化し、「仕組みを知る」「限界を示す」のような作業名だけで終えない。

### 分解を終える条件

各項目で、理解の対象となる要素・関係・条件を特定できる粒度にする。
前提からその項目へ、子項目から親項目へ進む際に、新しい理解が暗黙に必要になる場合は、その理解を追加する。
読者の既知の内容と計画の項目だけで到達目標への経路がつながり、目的に必要な理解が具体化されたところで分解を終える。

理解の項目には本文、例の筋書き、図表の仕様や配置を含めない。比較が必要なら、比較によって理解すべき対象の違いを定める。
理解の項目と、一節や一段落との対応は計画の完成条件にしない。

### 分解を止める粒度の例：雨

雨の説明のうち、水滴の雲ができる過程を取り出す。
この部分の目的は、空気の冷却から雲の水滴が生じるまでの因果を追えることとする。読者は、水に気体と液体の状態があることを知っていると仮定する。

**まだ粗い項目**

「水蒸気が水になる仕組みを理解する」。
この項目では、何が変化のきっかけになり、生じた水が雲にどうつながるかを、計画から特定できない。

**この目的に対して十分に分解した項目**

1. 空気中の水蒸気と、雲を作る水滴が、水の異なる状態であることを理解する。
2. 水蒸気を含む空気の冷却によって、凝結が起こる条件に達し、水滴が生じる関係を理解する。
3. 生じた微小な水滴が空気中に集まり、雲として見えることを理解する。

**ここで分解を止める理由**

変化する対象、変化が起こる条件、その結果と雲の関係を特定できた。読者の既知の内容と合わせて、「冷却→凝結→雲の水滴」という、この部分の目的に必要な因果が、三つの項目でつながる。

分子の熱運動や凝結の詳しい定量条件まで扱うかは、執筆目的と読者の前提から判断する。この例の目的では、上記の関係を特定できる粒度で止める。別の目的でその詳細が必要なら、対応する項目をさらに分解する。
これは一つの過程について止めどころを示す例である。雨のプラン全体では、蒸発や雨粒の成長・降下など、到達目標に必要な過程も同じ基準で確認する。項目数や思考段階の固定の型には使わない。

例の基礎となる冷却・凝結と水循環の関係は、[NASA「The Water Cycle」](https://gpm.nasa.gov/education/water-cycle)を参照する。

## 3. 執筆目的が満たされるか確認する

計画の完全性は、定めた執筆目的に必要な理解がそろっていることで判断する。

1. 執筆目的と文書が答える問いの各要素を、到達目標と理解の項目へ対応させる。
2. 到達目標から前提をたどり、読者の既知の内容または計画の項目で支えられているか確認する。
3. 各項目から到達目標へ進み、その理解が全体の理解や判断につながるか確認する。
4. 関連するだけの話題や、同じ理解を重ねて求める項目を整理する。
5. 必要な成立条件、適用範囲、根拠を踏まえて、到達目標が成立するか確かめる。

条件の違い、似た現象や隣接する技術、全体のシステムなどは、目的に必要な理解を支えるときに含める。粒度の例に登場した話題を、毎回の計画で必須にしない。
扱う範囲を定めた後も、到達目標に必要な理解がそろっているか確かめる。未解決の依存関係や根拠の不足が到達目標に影響する場合は、その影響を明示し、完成した計画として扱わない。

提示前に[reader-review.md](reader-review.md)に従い、読者ペルソナが既知の内容から到達目標へ進む経路と、必要な理解の不足を点検する。
目的に必要な指摘を計画へ反映し、分解を止める判断の理由と未解決事項を記録する。

## 4. 順序と根拠をそろえる

理解の項目を、Lv2から目標レベルへ進む順序に並べ、各段階との対応を示す。項目の階層と思考段階は、それぞれ理解の分解と積み上げ方を表す。番号をそのまま段階番号として扱わない。
前の段階で得る理解を次でどう使うかを明らかにし、初めて使う概念の前提をそろえる。
根拠には、理解の項目に対応する原典や観測記録を用いる。仕様、実例、実測で確かめられる範囲を区別し、未確認の内容と到達目標への影響を残す。仮定した例を実証の根拠にしない。

### 計画に含める情報

| 項目 | 記載する内容 |
|---|---|
| 目的と条件 | テーマ、執筆目的、想定読者と前提知識、文書が答える問い、目標レベル、扱う範囲。仮定は区別する。 |
| 到達目標 | 最終的に読者が理解すべき具体的な関係・条件・判断。 |
| 理解の項目 | 必要な理解の分解、項目間の前提とつながり、到達目標への対応。 |
| 理解を積み上げる順序 | Lv2から目標までの対応と、前の理解を次へつなぐ順序。 |
| 根拠と未解決事項 | 各項目に対応する資料と出典、事例・データの条件、確認状況、実証できる範囲、未解決の点と到達目標への影響。 |
| 計画の点検結果 | 読者ペルソナの条件、理解への経路、指摘の採否、分解を止める理由。 |
| 計画の状態 | 版、完成条件の確認状況、承認状態。ファイルに保存する場合は計画の保存先。 |

### 導入で必要な理解

仕組みや技術の導入では、読者の既知の作業や問いと、対象を必要とする理由をつなぐ理解を計画する。職位や隣接技術の経験だけで、導入の理由や内部モデルを既知の前提にしない。
開発の背景が理解に必要な場合は、原典で確認し、開発目的、現在の採用理由、仮定を区別する。複数の技術を組み合わせる場合は、それぞれが担う要求の違いを理解の項目にする。
詳しい内部構造や制御手順に進む前に、その前提となる理解をそろえる。

## 5. 計画を提示し、承認状態を記録する

計画の冒頭に、依頼者が方針を判断できる短い承認用の要約を置く。要約には次をまとめる。

- テーマ、執筆目的、想定読者、必要な前提と目標レベル。
- 到達目標と、それを満たす主要な理解の項目。
- 理解を積み上げる順序と、根拠の確認状況。
- 扱う範囲と、計画の完成条件の確認状況。
- 方針や到達目標に影響する、依頼者の判断が必要な未解決事項。

要約の長さは、主要な判断を一読できる量で決める。理解の項目、前提とつながり、出典、確認状況、点検結果は詳細に記録し、要約の後へ置く。媒体に応じて、折りたたみや詳細へのリンクも使う。短い計画では要約と必要な詳細を一つのまとまりで示してよい。

依頼者には、執筆目的、読者、到達目標、理解の順序、扱う範囲を確認してもらい、計画の承認を求める。根拠の確認と、理解の項目・つながりの不足の点検は、計画担当が実施する。依頼者の判断が必要な点や、到達目標の成立に影響する制約は、要約に示す。

要約と詳細を一つの計画として管理し、変更した場合は両方の対応を確認する。
承認待ち・修正中・承認済みを区別する。質問や修正の依頼は、計画を直す指示として扱う。時間の経過や計画の保存・コミットを承認とみなさない。
会話ですでに具体的な計画が承認されている場合は、その承認を引き継ぐ。読者、目標レベル、主要な到達目標や扱う範囲を変更する場合は、影響する変更点を提示して承認を得る。
同じ到達目標を支える項目や根拠の補強、誤りの修正は、承認された範囲で進める。
複数の計画は、それぞれの到達目標と必要な理解が具体化されていれば、まとめて承認を得てもよい。
ユーザーが承認を省くよう明示した場合は、その指示を優先し、承認を省略した状態を記録する。

理解の項目、前提、順序、根拠の確認状況、点検結果がそろった計画を成果物とする。
目的に必要な不足が残る場合は、その内容と影響を示し、完成条件を満たしているかと承認状態を別々に記録する。
計画の提示・修正と承認状態の記録で、このスキルのタスクを終える。
