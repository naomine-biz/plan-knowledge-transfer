# 知識移転を計画する

テーマと想定読者を入力に、各段階で何を説明し、どう到達点へつなぐかを計画する。
新しい技術的説明の執筆、または論旨を大きく組み直す場合に、依頼者へ提示して承認を得る。
目標レベルと説明の順序は[thinking-levels.md](thinking-levels.md)に従う。

## 1. 入力と到達点をそろえる

依頼と既存の文脈からテーマ、想定読者、読者の前提知識、文書が答える問い、扱う範囲を確認する。
目標レベルが不明な場合は、根本思想の手順に従ってHumanに確認する。
その他の未指定事項は、計画に仮定と影響を示す。説明の成立に関わる前提が不明な場合は確認する。

独立したテーマを並べるカタログでは、章などの単位で到達点と説明を設計する。読者、共通の前提、比較軸は全体でそろえ、章間で必要な前提も示す。

書き手が目標レベルの説明そのものを先に作り、計画に載せる。
「読者が全体を理解できる」のような到達状態だけで済ませず、実現されるシステムや戦略の関係と成立条件を説明文にする。

## 2. 段階ごとの説明を設計する

計画には次を含める。依頼の規模に合わせ、短い説明では簡潔な表や箇条書きで示してもよい。

| 項目 | 記載する内容 |
|---|---|
| 執筆条件 | テーマ、想定読者と前提知識、文書が答える問い、目標レベル、扱う範囲、媒体・文体。仮定は区別する。 |
| 到達点の説明 | 先に作ったLv5またはLv6の説明文。後の本文で裏付ける主張と成立条件が分かるようにする。 |
| 段階別の内容 | Lv2から目標まで、それぞれで説明する具体的な論点、使う前提、例・反例、根拠、次の段階へつなぐ関係。 |
| 本文の構成 | 章や節など、説明のまとまりと段階別の内容の対応。各節で全段階を繰り返す必要はない。 |
| 承認後の制作工程 | 草稿の執筆、技術説明の推敲、読みやすさの推敲、完成稿と計画の照合の順序。各工程の入力・作業・完了条件・次へ渡す成果物と、推敲で保つ内容。 |
| 材料と未解決事項 | 主張に対応する資料と出典、事例・データの対象と条件、測定方法、確認済み・要確認の区別、実証できる範囲、未解決の点と本文への影響。 |
| 成果物 | 本文の形式と保存先。比較用の版を求められた場合は、保持する原稿と新しい保存先。 |

段階名や「反例を検証する」といった作業名だけで計画を終えない。
そのテーマのどの関係を説明し、どの反例で条件を確かめ、どの材料がどの主張を支えるかを具体化する。
前の段階で説明した概念を次でどう使うかを示し、根拠の不足によって到達点が成立しない場合は、先に計画を修正する。
根拠には、その主張を支える原典や観測記録を用い、仕様の説明、実測、仮定した例を区別する。
確認していない材料で到達点を裏付けたことにせず、未確認の主張と計画への影響を残す。

### 導入の問題設定と説明の順序

読者の既知の作業や具体的な問いから、求める結果、従来の方法で負担や制約になること、その条件、対象技術が満たす要求を説明する。職位や隣接技術の経験だけで、対象技術が必要になった理由や内部モデルを既知の前提にしない。

開発の背景は、問題設定や設計の選択を理解するために必要な範囲を原典で確認する。開発目的、現在の採用理由、説明用の想定を区別する。複数の技術を組み合わせるテーマでは、それぞれがどの要求を担うかを示す。

次に、その要求から仕組みや操作を一段ずつ説明する。新しい用語には、それを導入する理由と具体例を対応させる。部品の一覧や詳細な制御手順は、内容を理解するための前提を説明した後に置く。主線の問いに不要な詳細は補足へ配置し、必要な因果や成立条件は本文に残す。

### 承認後の制作工程

計画には、以下の各工程の入力・作業・完了条件・次へ渡す成果物を、対象の原稿に合わせて記載する。エージェントは実行時に、工程で必要な能力と環境で利用可能なスキルを照合し、適したものを選んで使う。該当するスキルがない場合は、工程に定めた作業と完了条件に沿って進める。

| 工程 | 入力 | 作業 | 完了条件と次へ渡す成果物 |
|---|---|---|---|
| 草稿の執筆 | 承認された計画、例、根拠資料。 | 説明の順序を文章・図表へ展開する。用語を導入する理由と前提を説明する。 | 計画の論点が草稿の箇所に対応し、出典と未確認事項が分かる草稿を渡す。 |
| 技術説明の推敲 | 草稿、計画、根拠資料。 | 論証、用語の導入、例と主張、出典、成立条件を確認し、必要な説明を補う。 | 到達点までの論理と前提がつながり、主張が根拠の支える範囲に収まっている。修正した草稿と未解決事項を渡す。 |
| 読みやすさの推敲 | 技術的に整えた草稿。 | 意味を保ち、主述、修飾、指示語、文のつながりや不自然な表現を整える。 | 主張・条件・文体を保ち、文と段落の関係を追える原稿を渡す。 |
| 完成稿と計画の照合 | 推敲後の原稿、承認された計画。 | 到達点に必要な各主張と条件を説明した本文の箇所を照合する。 | 必要な説明と段階のつながりがそろい、未実証の範囲が明示されている。完成稿と未解決事項を渡す。 |

文章規範や検査の具体的な手順は、その工程で選んだスキルや方法に従う。文書の立場と文体を計画に定め、読みやすさの推敲では主張、比重、断定の強さ、文の働き、数値、条件、因果、出典を保つ。文長や装飾量の目安を、必要な説明を削る理由にしない。

説明不足や意味の変化が見つかったら技術説明の工程へ戻り、根拠を確認して修正し、その箇所を再び推敲する。工程名だけで終えず、何を確認して次の工程へ渡すかを記載する。

## 3. 計画の承認を得る

到達点の説明と承認後の制作工程を含む計画を依頼者へ提示し、本文を執筆してよいか確認する。
ファイルを作る場合は、読者向け原稿と分け、承認待ち・承認済み・修正中を区別する。
明示的な承認や、その計画で執筆を進める指示を得るまで、本文の生成を始めない。
質問や修正の依頼は、計画を直す指示として扱う。時間の経過や、計画の保存・コミットを承認とみなさない。

承認済みの計画の範囲では、節ごとの執筆や継続のたびに承認を取り直さない。
複数章の計画は、到達点と制作工程が具体化されていれば、まとめて承認を得てもよい。
読者、目標レベル、主要な論旨や扱う範囲を変更する場合は、影響する計画の変更点を提示して承認を得る。
同じ到達点を支える説明や根拠の補強、誤りの修正は、承認された範囲で進める。
既存原稿のレビューや、論旨を変えない局所的な推敲・誤字修正に、新たな計画の承認を要求しない。
会話ですでに具体的な計画が承認されている場合は、その承認を引き継ぐ。計画の提示前に受けた一般的な執筆依頼だけで、計画を承認済みとは扱わない。
ユーザーが計画の承認を省いて進めるよう明示した場合は、その指示を優先する。

## 4. 承認された計画を執筆工程へ渡す

計画は依頼者と書き手が説明内容を確認するために使う。
完成稿への展開は[執筆の判断を本文へ展開する](thinking-levels.md#執筆の判断を本文へ展開する)に従う。
想定読者や段階の到達状態を記載した計画を、そのまま読者向け本文へ流用しない。

執筆工程には承認された計画を渡し、各工程の入力・作業・完了条件に従って進める。段階ごとの内容を別の計画として重複管理しない。
計画や完成した説明の確認は[review-checklist.md](review-checklist.md)に従い、主張と関係を説明した本文の箇所を照合する。
