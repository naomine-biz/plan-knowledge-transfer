# 読者ペルソナによるレビュー

読者役の応答を使い、目的に必要な理解とつながりの不足を点検する。
計画では理解へ至る設計を、草稿では実際に書かれた説明を評価する。計画の提示前と、草稿を計画に照合する工程で使う。

## 1. 読者役の条件を定める

計画の想定読者から、代表となる読者ペルソナを一つ設定する。

- 読者の役割と、説明を読む目的。
- 目標レベル。Lv5かLv6かは、計画と[thinking-levels.md](thinking-levels.md)に従う。
- 対象テーマについて既に知っている概念・関係。
- これから獲得する理解と、既知と仮定していない事項。

思考レベルは、そのテーマについて目指す理解として設定する。高度な職位や目標レベルから、対象テーマの基礎知識を追加で仮定しない。
未指定の前提は仮定として記録する。レビュー結果を良くするために、途中で読者の前提知識を増やさない。

別の文脈で読者役を実行できる場合は、対象の計画または草稿、読者の条件、このレビュー手順を渡す。書き手の修正意図、疑っている欠陥、期待する応答は渡さず、読者役に問いと不足を挙げてもらう。
同じエージェントで役割を切り替えて実行する場合は、その条件を評価記録に残す。

## 2. 対象に合わせて応答を得る

### 計画のレビュー

読者役には、到達目標、理解の項目、その前提とつながり、読者の条件を渡す。
完成稿の理解を判定する代わりに、次を確認する。

1. 到達目標を満たすために答えられるべき問いを挙げる。
2. 既知の内容から、計画の項目を経て到達目標へ進む経路を示す。
3. 各問いで必要な理解を、計画の項目へ対応させる。
4. 経路の途中で追加の前提が必要になる箇所や、理解の対象が曖昧な項目を指摘する。

計画にある具体的な関係や条件を評価する。本文で扱う説明がまだ書かれていないこと自体を、不足の理由にしない。
「条件を理解する」のように、条件の対象や関係を特定できない項目は、何を具体化すべきかを挙げる。
この段階の応答は設計の評価として記録し、本文を理解できた証拠には使わない。レビューのために本文や図表の案を追加しない。

### 草稿のレビュー

読者役には、草稿、計画の到達目標と理解の項目、読者の条件を渡す。

1. 到達目標に関わる因果、条件、全体の動作や判断を、自分の言葉で説明し直す。
2. 草稿で扱う条件を変えた問いや、成立範囲を確かめる問いに応答する。
3. 各応答を支える本文の箇所を示す。読者の既知の内容で補った部分も区別する。
4. 説明できない関係、複数の解釈が残る箇所、本文の根拠が見つからない応答を挙げる。

本文にない知識で補った応答は、本文の説明が十分である証拠にしない。読者の前提知識として定めた内容を使うことと、新しい知識を補うことを区別する。

## 3. 応答を照合して修正を決める

書き手は、読者役の応答を計画、本文、根拠資料へ照合する。
「理解できた」「十分だった」という自己申告に加えて、理解への経路、説明し直した内容、問いへの応答とその根拠を確認する。

指摘ごとに、次の扱いを決める。

- **目的に必要な不足**：足りない前提、因果、条件、区別を具体化し、該当する項目を分解するか、草稿の説明を補う。
- **根拠の不足や応答の誤り**：資料を確認し、説明と応答のどちらに修正が必要かを判断する。
- **目的の範囲外の追加質問**：到達目標への寄与を確認し、採否を決める。質問が出たことだけを、説明を増やす理由にしない。
- **読者の前提が合わない指摘**：設定した前提との対応を確認する。前提自体を変更する必要がある場合は、その影響を計画に戻す。

修正後は、変更した項目や本文の箇所と、その前後のつながりを再確認する。
到達目標、読者、主要な範囲が変わる場合の承認は、[knowledge-transfer-plan.md](knowledge-transfer-plan.md)に従う。

## 4. 分解を止める判断と記録

分解を止める目安は、設定した前提のもとで、目的に必要な理解への経路がつながり、必要な不足が解消されていることとする。
計画では、問いに必要な理解を具体的な項目へ対応できることを確認する。草稿では、説明し直した内容と問いへの応答が、本文と根拠に照らして成立していることを確認する。
新しい質問が出なくなることや、読者役の全員一致を終了条件にしない。

結果は簡潔に記録する。

- 対象の版、計画か草稿か、読者の条件、別文脈か同一エージェントか。
- 理解への経路、または説明し直した内容と主要な問いへの応答。
- 根拠となる計画の項目や本文の箇所、解消した不足、残る不足と目的への影響。
- 範囲外の質問の採否と、分解を止める判断の理由。

結果は「目的に必要な不足がある」「この条件では必要な不足を見つけていない」「評価材料が不足している」など、確認した範囲が分かる形で示す。
これは仮想の読者による点検である。実際の読者による検証、資料に基づく技術的な確認、Humanによる計画の承認は、それぞれの工程として扱う。
