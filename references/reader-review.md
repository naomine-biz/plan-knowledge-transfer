# 読者ペルソナによる計画の点検

読者役の応答を使い、知識移転計画に必要な理解とつながりの不足を点検する。
計画の提示前に、理解へ至る経路と分解の止めどころを確かめる。

## 1. 読者役の条件を定める

計画の想定読者から、代表となる読者ペルソナを一つ設定する。

- 読者の役割と、説明を読む目的。
- 目標レベル。Lv5かLv6かは、計画と[thinking-levels.md](thinking-levels.md)に従う。
- 対象テーマについて既に知っている概念・関係。
- これから獲得する理解と、既知と仮定していない事項。

思考レベルは、そのテーマについて目指す理解として設定する。高度な職位や目標レベルから、対象テーマの基礎知識を追加で仮定しない。
未指定の前提は仮定として記録する。点検結果を良くするために、途中で読者の前提知識を増やさない。

別の文脈で読者役を実行できる場合は、計画、読者の条件、この点検手順を渡す。計画担当の修正意図、疑っている欠陥、期待する応答は渡さず、読者役に問いと不足を挙げてもらう。
同じエージェントで役割を切り替えて実行する場合は、その条件を点検記録に残す。

## 2. 理解への経路を確かめる応答を得る

読者役には、到達目標、理解の項目、その前提とつながり、読者の条件を渡し、次の応答を得る。

1. 到達目標を満たすために答えられるべき問いを挙げる。
2. 既知の内容から、計画の項目を経て到達目標へ進む経路を示す。
3. 各問いで必要な理解を、計画の項目へ対応させる。
4. 経路の途中で追加の前提が必要になる箇所や、理解の対象が曖昧な項目を指摘する。

計画にある具体的な関係や条件を評価する。本文がまだ書かれていないこと自体を、不足の理由にしない。
「条件を理解する」のように、条件の対象や関係を特定できない項目は、何を具体化すべきかを挙げる。
応答は計画の点検結果として記録する。応答を得るために本文や図表の案を追加しない。

## 3. 応答を照合して計画の修正を決める

計画担当は、読者役の応答を計画と根拠資料へ照合する。
「理解できた」「十分だった」という自己申告に加えて、理解への経路、問いと項目の対応、前提と根拠を確認する。

指摘ごとに、次の扱いを決める。

- **目的に必要な不足**：足りない前提、因果、条件、区別を具体化し、該当する項目を分解するか、項目間の関係を修正する。
- **根拠の不足や応答の誤り**：資料を確認し、計画と応答のどちらに修正が必要かを判断する。
- **目的の範囲外の追加質問**：到達目標への寄与を確認し、採否を決める。質問が出たことだけを、項目を増やす理由にしない。
- **読者の前提が合わない指摘**：設定した前提との対応を確認する。前提自体を変更する必要がある場合は、その影響を計画に戻す。

修正後は、変更した項目と、その前提・依存先・親項目へのつながりを再確認する。
到達目標、読者、主要な範囲が変わる場合の承認は、[knowledge-transfer-plan.md](knowledge-transfer-plan.md)に従う。

## 4. 分解を止める判断と記録

設定した前提のもとで、目的に必要な理解への経路がつながり、問いに必要な理解を具体的な項目へ対応でき、必要な不足が解消されたところで分解を止める。
新しい質問が出なくなることや、読者役の全員一致を終了条件にしない。

結果は簡潔に記録する。

- 計画の版、読者の条件、別文脈か同一エージェントか。
- 理解への経路と、主要な問いに対応する計画の項目。
- 解消した不足、残る不足と目的への影響、根拠の確認状況。
- 範囲外の質問の採否と、分解を止める判断の理由。

結果は「目的に必要な不足がある」「この条件では必要な不足を見つけていない」「点検材料が不足している」など、確認した範囲が分かる形で示す。
これは仮想の読者による計画の点検であり、実際の読者の理解を実証するものではない。根拠の確認とHumanの承認も、それぞれの結果として記録する。
